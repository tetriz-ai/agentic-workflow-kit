# Skill: Building a Task Breakdown

The bridge between a **reviewed RFC** and an **autonomous shipper**. `/plan:tech-design-doc-writing`'s `sections/task-breakdown.md` (at `${CLAUDE_PLUGIN_ROOT}/skills/tech-design-doc-writing/sections/task-breakdown.md`) defines the **contract** — the columns and the review hooks. This skill is the **builder** that fills that contract, so `/queue:ship-queue --integration-branch` can drain the whole design in dependency order and `/queue:ship-task` can take any one slice end-to-end.

The writing skill produces a *first cut* of the breakdown; this skill **hardens it after review** — the rigorous, grounded pass that verifies every dependency edge and touch-point against the real code. **Read [reference.md](reference.md) before your first run** — it carries the HITL rule, DAG-validation, the ground-verify fan-out, the worked example, and why this is a separate skill.

## When to run, and on what

- **Input:** an RFC that has **passed `/plan:tech-design-doc-review`** — a `PASS` or `PASS (self-administered)`, since a `SCOPED PASS` means part of the doc is still ungraded (the design is settled; you are slicing a reviewed design, not an in-flux one). If the RFC still has open mechanism forks (per `sections/lld.md`), it is **not ready** — slicing a design with undecided mechanisms produces speculative, over-granular slices. Send it back to the writing skill first.
- **The RFC usually already carries a first-cut Task Breakdown** — the writing skill drafts one. Treat it as **input to harden, not to ignore**: build your grounded breakdown, then diff it against the first cut — keep what holds, correct what grounding disproves, and explicitly note any slice you drop, merge, or add. In default (in-RFC) mode you are *replacing* that section with the hardened version, so don't silently discard a human edit you can't improve on.
- **Output target — configurable:**
  - **Default: into the RFC's `## Task Breakdown` section.** The contract lives there and the shippers read the RFC, so this is the single source of truth. This is the normal path.
  - **Standalone artifact** when the RFC is **frozen** (e.g. merged, or under separate review and you must not edit it): emit the breakdown as its own file and link it from the RFC. Splits the source of truth, so use it only when editing the RFC in place is not allowed.
  - Ask which applies only if it is genuinely ambiguous; default to in-RFC.
- **Scope boundary:** this skill builds the **breakdown**, never the **design**. If slicing surfaces a design gap (a missing mechanism, an unanswered fork), that goes **back to `/plan:tech-design-doc-writing`** as a fork — do not paper over it in a slice.

## The build — the steps

Run them in order. Step 3 is the one that separates a grounded breakdown from a plausible one; step 5b is the one that keeps the drain from stalling on gates nobody needs, or sailing past one somebody did.

### 1. Inventory the build surfaces
From the design (HLD + LLD + concerns + flags + rollout), list **every** surface the change implies — do not stop at the feature code. The recurring surfaces: API contracts (proto or similar) · schema + migration + data access · internal services · API gateway / BFF · scheduler · operational jobs · frontend · feature flags · observability (metrics/dashboards/warehouse watch) · testing · **quality-evaluation harness** (where §7's output-quality concern applies — the sample, the rubric or gold set, the runner; it is build work, not something the eval acquires by itself) · docs/terminology (sequenced last — see step 6) · rollout/runbook · **ADR extraction · harness education** (the two RFC-tail terminal slices — see below; defined in the contract). A breakdown that lists only the feature code is incomplete — the supporting surfaces are slices too (this is the writing skill's "whole-RFC completion" rule, enforced here).

**Terminal persona-run slice (user-facing features).** When the feature is user-facing, add a final **persona-run** slice that **depends on all the feature slices** — an ordering-only *sequencing* edge (step 3 keeps it, recognised by the persona-run slice type, rather than pruning it as spurious), and the deliberate exception to step 2's "avoid a wide union" caution, since the persona run's whole purpose is to gate on the fully assembled feature. Its job is to exercise the *assembled* feature end-to-end **as the new target persona** on a real run. It is distinct from the integration-test slice (an automated suite) and the rollout/deploy-smoke slice (the deploy works): the persona run is "a human-equivalent actually used the thing as the persona it was built for, and it held." If an existing slice (the integration-test slice, or a DoD section) already carries that persona end-to-end run, **do not add a second row** — annotate that slice's proof as the persona-run evidence; emit a distinct persona-run slice only when no slice carries the run. Its proof shape is in step 7.

**Terminal RFC-tail slices (every RFC).** Beyond the persona-run slice, every RFC closes with two terminal slices the **contract** (`tech-design-doc-writing/sections/task-breakdown.md`) defines — an **ADR-extraction** slice and a **harness-education** slice — each depending on all the feature slices (a sequencing edge step 3 keeps). Read the contract for what each *is* and how it *proves* — do not restate it here; the harness-education slice is two-phase (a best-effort prediction at breakdown time, re-grounded at pick time). The **builder's** job is narrower: (a) ground the harness-education slice's *predicted* touch-points like any other — confirm the `.claude/rules` / `CLAUDE.md` / skill files it names to enrich actually exist where claimed (step 3); (b) keep both slices' sequencing edges (step 3) and cover them in the DAG (step 6). If the RFC's first cut omits either, add it.

### 2. Slice into vertical units
A **slice** is a unit of behaviour change that **crosses a layer boundary and can be asserted in isolation** — input → observable output through the real path. Not "the DAO method" alone, but "the DAO method wired far enough to assert the number it returns." Group naturally-atomic work (a proto + its first consumer can be one slice); split a slice that needs *two* build skills unless it is genuinely atomic. Give each slice a stable **ID** (the shippers and the `depends-on` edges reference it).

**Grouping-default — fewer thin slices.** The split signal above (two build skills) biases toward *splitting*; balance it with a consolidation default, because every slice carries the full per-slice tax (JIT issue → grounding subagent → worktree → review panel → Codex sweep → the merge gate → live-e2e → merge), which dwarfs a thin change. **Slices that share an implementing skill and the same layer/surface are one slice by default** — its demoable proof is the *conjunction* of the pieces' asserts. Split them only on a **forcing signal**: a downstream slice depends on one piece but not the others — a merged slice inherits the **union** of its pieces' `depends-on`, so it drains no earlier than its latest dep, and merging would stall that dependent behind deps it never needed; the pieces carry **different HITL tags**; or a piece's proof genuinely **cannot be asserted in the same run** as the others. The concrete test is: merge only when the wider union delays **no** dependent of any piece. "Each piece has its own assertion" is **not** a forcing signal — co-asserting them in one slice is exactly the point. Two worked cases — one merges, one does **not**, which is how you see the forcing signal earn its keep (check each downstream-dependency claim against the breakdown's `depends-on` column; don't take the prose on faith):
  - **Merges:** three operational-job slices (all carrying the `none — operational job` implementing-skill value, all anchored to the RFC's operational-jobs section, each a thin READ/EXECUTE mode) → one **operational jobs** slice. The decisive fact is that **nothing downstream depends on any of the three**, so no forcing signal fires.
  - **Stays split (despite sharing skill + surface):** two API-contract slices for an invented widget feature (same implementing skill, both produced by one code-generation run) *look* just as mergeable — but several downstream slices depend on the **widget-status enum** slice (W1a) and **not** the **widget RPC** slice (W1b). Merging them would stall those slices behind W1b's RPC work, so the divergent-downstream forcing signal fires and they **stay two slices** (the foundation reviews them together, but they ship separately). Same skill + same surface is the default to merge; a divergent downstream dependency overrides it.

### 3. Ground-verify every edge and every touch-point — do not assume
This is the differentiator. For **each** slice and **each** `depends-on` edge, confirm against the **actual code**, not the design's assumption:
- **Touch-points** — does the package/file/table the slice claims to touch exist where the design says? Is a field a **proto** field or a **Go-struct** field (they land in different slices)? Does the column already exist in the schema snapshot?
- **Edges** — is the `depends-on` real (slice B truly needs a symbol/table/contract slice A introduces), or spurious (they only *look* related)? Is there a **missing** edge (B reads a column A adds, but the edge isn't drawn)? **One deliberate exception to "real = consumes a symbol": an ordering-only *sequencing* edge** — a docs/terminology slice depending on the code it narrates (step 6), the terminal persona-run slice depending on the feature slices it exercises (step 1), or the RFC-tail ADR-extraction / harness-education slices depending on the feature slices they close out. It consumes no symbol but enforces drain order, so it is **not** spurious and **must not be pruned** — recognise it by its **source slice's type** (a docs/terminology, persona-run, ADR-extraction, or harness-education slice), not by a cell marker: the `depends-on` cell stays bare slice IDs (so the drain still orders on it), and this pass keeps the edge instead of mistaking it for a mis-drawn data edge.
- **Cross-tier skips** — a dependency that crosses tiers (schema → API contract, a job → its scheduler) is the easiest to get wrong; trace it.

**Mechanism:** fan this out to subagents — one per cluster of edges/touch-points — each handed the slice rows and told to verify against the schema snapshot + the named packages and return corrections. Dispatch heavy verification to subagents; fold their corrections back. (reference.md has a worked example of the corrections this pass makes.)

### 4. Self-sufficiency check (per slice)
For each slice ask: **can an agent build this from its referenced RFC section alone**, without scavenging backward through the prose? Each slice names its **RFC anchor** (the section(s) it implements); that section must be complete *for that slice*. Flag every under-specified slice, then apply this test to pick the fix: **does the RFC's LLD or Decisions Log actually contain the mechanism the slice needs?** If yes → the fix is a **tighter anchor** (name the extra section, or draw the missing `depends-on` edge that supplies it). If the RFC is **silent** on the mechanism — no section, no decision row → that is a **design gap**; send it back to the writing skill (step boundary above). Run the test; don't default to "add an edge" without it.

### 5. HITL tag — the three-category rule
Tag each slice by **where a human decision sits**, not by how "sensitive" it feels (the anti-pattern is "sensitive ⇒ gate"). The three categories — **open-decision · run-time-gated · expensive-to-discover-late** — and the foundation-collapse rule are defined in [reference.md](reference.md); **read that section before tagging** — the labels here are an index, not the rule.

### 5b. The autonomy second pass — re-examine every tag against the code
Step 5 tags; this step audits the tags, and it is the half only the builder can do. The contract (`tech-design-doc-writing/sections/task-breakdown.md`) states the pass and its first two questions — what the human adds that the automated gates cannot, and whether the Decisions Log already settles it — both answerable from the RFC, so the writing skill has already run them on the first cut. **Re-run them anyway** (the first cut may predate a Decisions-Log row that has since closed), then run the third, which needs the codebase:

**Can a guardrail plus an executable completion check carry what the human was going to do?** A guardrail is a mechanism that makes the bad outcome impossible or loud — an arch test, a lint rule, a merge-gate check, a migration dry-run with a reversibility assertion, an RLS-scoping test, a rollback drill. The completion check is the slice's own demoable proof, strengthened to fail on the thing the human would have caught.

**Bind every conversion three ways** (why each binding exists: [reference.md](reference.md)'s guardrail section):

- **Cite the guardrail as a `file:line`** — the assertion that would actually fail on the defect — or as an in-breakdown slice ID. A bare name does not count; "we will be careful" and "the panel will catch it" are not conversions.
- **A guardrail that is itself a slice gets a real `depends-on` edge**, not a prose mention (step 6 DAG-validates it like any other). If that slice is later dropped, re-run this step for its dependents.
- **Do not convert an author-set tag.** Where the Decisions Log records the human choosing it, converting is a fork back to the human — `UNRESOLVED (NEEDS HUMAN)` if none is reachable. The *add*-a-gate half stays unrestricted.

When the guardrail genuinely cannot be built at reasonable cost, **the gate stays and the slice records why in one line** — so a surviving gate is a reasoned residue rather than a default.

The pass runs **both directions** (contract, same bullet): an autonomous slice whose defect is expensive to discover late and which no existing guardrail covers **earns a gate**. Read [reference.md](reference.md)'s HITL section before running this step — the three categories it audits against are defined there, and this step is the audit, not a second definition of them.

### 6. DAG-validate
Check the whole graph: **no cycles**; **every surface from step 1 covered exactly once** (nothing dropped, nothing duplicated); **supporting work included** (tests, observability, flags, operational jobs, docs, rollout). A surface in the inventory with no slice is the bug this step catches. **Docs land last.** A terminology / architecture-docs slice documents *shipped reality*, so it must sort **after** the code slices it describes — never Wave 0. The **ADR-extraction** and **harness-education** RFC-tail slices land last for the same reason — the harness-education slice re-grounds against *shipped* code, so it cannot precede it — encoded the same way: a real `depends-on` edge on the feature slices. Encode this as a **real `depends-on` edge** on those code slices: the drain orders strictly on the `depends-on` column, so a prose note like "ship after X merges" is invisible to `/queue:ship-queue` and will not reorder it — write the edge, not just the note. The dependency is "soft" only in intent (the docs slice does not *consume* a symbol the code defines); in the table it is a normal slice-ID `depends-on` edge (so the drain orders on it), and step 3's ground-verify keeps it as a sequencing edge — recognised by the docs-slice type — rather than pruning it as spurious. A docs/terminology slice left at `depends-on: —` that rewrites the vocabulary ahead of the proto/schema/provisioning code it narrates is the bug this catches: it commits a rename against a design assumption the code may still disprove. **Two slices touching the *same* file are not automatically a duplication** — if they are genuinely separate edits with separate proofs and deps (e.g. a config-keyed op *skip* vs queue *routing*, both at schedule-build), record both and note the intentional same-surface split. That is distinct from the **cap-fold anti-pattern** (one concern wrongly split across two slices), which collapses into one.

### 7. Emit the machine-clean table
Produce the table the shippers consume, **aligned 1:1 with [task-brief.md](task-brief.md)** (so one issue per slice is mechanical). Columns:

```
| # | Slice | Layers crossed | Demoable proof | HITL/AFK | Depends-on | RFC anchor | Implementing skill |
```
The column names must match the contract (`sections/task-breakdown.md`) **exactly** — the shippers parse on them. **Demoable proof, RFC anchor, Depends-on, and the Implementing-skill values are all *defined* in the contract — fill each per that definition; do not re-derive them here** (demoable proof is never a screen; the non-slice, config, persona-run, ADR-extraction, and harness-education proof shapes all live there; `Depends-on` is bare slice IDs = the DAG edge the drain orders on). Two cell *formats* the builder owns (not in the contract):
- **HITL/AFK** — emit the contract's canonical value literally, `human-gated` or `autonomous`, optionally followed by a one-word reason as annotation. Do not invent a glyph legend or a synonym: the accepted-token table and the resolution rule live in the contract (`tech-design-doc-writing/sections/task-breakdown.md`) and are deliberately not restated here, because a partial copy of a token set is how this gate goes inert.
- **Implementing-skill parse key** — the leading token (`/skill` or `none`) is what the shippers route on: never a silent empty cell, never a bare `— reason` without `none`. A slice may annotate `via <agent-name>` when the repo has a dedicated agent for that surface; `/queue:ship-queue` dispatches the build through that agent off the slice's skill (the annotation is not a separate value).

Surround the table with the framing the shippers and reviewers rely on: the **execution strategy** (how `/queue:ship-queue` drains it), the **done+verified bar** per slice (the proof passed *and its evidence is in the PR*; the merge gate green; review-panel Critical/Important cleared; flag stays default-off so it merges dark), any **reviewed-together** note (the foundation collapse from step 5), and any **not-a-slice** pre-merge design item (call it out explicitly so it is not mistaken for build work). Two more the framing must carry:

- **The grounded stamp plus its per-edge record**, in the form the contract defines (`sections/task-breakdown.md`). Step 3 already produced the per-edge evidence; write it down rather than collapsing it to a count. Emit neither unless step 3 actually ran.
- **The step-5b roll-up, in both directions.** How many slices **stayed gated**, with the one-line residue reason each carries; and every slice **converted** to autonomous, with the guardrail identity it was converted on and which of the three categories that discharged. Reporting only the survivors would leave the riskier direction with no artifact at all. Together this makes over- *and* under-gating visible without a quota, which would only push honest tags into dishonest ones.

## Verify the build
Before handing off: the table **parses** into `/queue:ship-queue`'s consumption (every slice has all columns; the column names match the contract exactly; every `depends-on` references a real slice ID); every surface from step 1 has a slice; the DAG has no cycle. **Always re-verify every cross-tier `depends-on` edge** (schema→API contract, data access→API layer, a job→its scheduler) as an independent pass — a fresh subagent re-checks them (and honours step 3's sequencing-edge carve-out — an ordering-only docs/persona-run edge, recognised by its source slice type, is kept, not pruned) — and re-run the full step-3 ground-verify when the breakdown has **≥ ~15 slices or any cross-tier edge**. The trigger is structural, not a judgment call: a wrong edge is the costliest defect because it misorders the autonomous drain.

## Boundaries (do not drift)
- **Builder, not contract.** The columns and review hooks live in `tech-design-doc-writing/sections/task-breakdown.md`; this skill fills them, it does not redefine them. A new column is a contract change there, not here.
- **Breakdown, not design.** Never edit the RFC's design sections; a design gap goes back to `/plan:tech-design-doc-writing`. In standalone mode, never edit the RFC at all.
- **Not the shipper.** `/queue:ship-queue` drains the breakdown and `/queue:ship-task` takes one slice; this skill does not build slices, create tickets, or run the merge gate. Ticket creation is `/queue:ship-task`'s just-in-time job per slice (from [task-brief.md](task-brief.md)).
- **Honest cells only.** No silent empty implementing-skill cell; no `depends-on` to a slice that doesn't exist; no surface dropped from the inventory without saying so.
