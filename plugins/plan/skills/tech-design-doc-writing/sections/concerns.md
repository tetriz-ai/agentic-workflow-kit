# §7 Cross-Cutting Concerns

**What it is** — the seven concerns we keep discovering *late*, after the code ships. Front-load each that applies as a **named question**, not a generic "did you consider non-functionals?"
**Applies when** — raise each concern only where it applies; a *defensible explicit skip* passes, a silent omission of an applicable concern fails.

## 1. Data / analytics correctness (the wrong-numbers class)
*Applies when the change emits a number a human reads or acts on. Output that is **graded** rather than computed — a summary, a classification, a ranking — is concern 7, not this one.*
> What is the **correct** number, and what proves it? Walk the computation: is the denominator right (an un-normalised ratio lies), is the numerator bounded, how does it round, how does it behave at low sample (a median over 8 is noise)? Are two different statistics compared as one (within-org vs cross-org)? If every emit site must agree on a scale (per-day vs per-week, fraction vs %), is that consistency checked?
- A fixture/known-input test that asserts the hand-computed expected output is **one good way** to lock this — not a mandate (don't force a golden-JSON ritual). The point is: design the proof in.
- **A migration/backfill that skips a subset must reconcile its parity gate against the skip — and the carve-out must be check-time-computable.** When a migration or backfill intentionally drops rows (a size guard skips oversized values, a filter excludes a class), a strict *zero-mismatch* parity gate is **unsatisfiable** — the source holds keys the target never gets, so the go/no-go gate can never pass. The bar is **zero *unexpected* mismatch**, reconciled against the skipped set. And that carve-out must be **computable at check time from persisted state** — a column, or a predicate re-derivable in the parity SQL (`octet_length(settings->'cache'->key) > cap`) — **never** a runtime-only signal (a Prometheus counter / log line has no per-key identity to join into the per-key parity query). Otherwise the gate is either unsatisfiable or silently self-asserted (a bypass anyone can grant by assertion is no gate). This is the family where a **second mechanism (the skip) quietly invalidates a first (the gate)**; the same shape as the growing-table eviction-trigger and the CDC-cost checks.
- **Review hook:** an analytics RFC with no statement of the right number / how it's verified → FAIL. A **migration/backfill with a skip/filter whose zero-mismatch parity gate does not carve out the skipped set, or carves it out via a runtime-only signal not re-derivable at check time** → WARN.

## 2. Observability — two layers
*Applies to anything that runs in prod and can misbehave silently.*
- **Real-time (e.g. Prometheus):** the metric + alert threshold that says it's erroring *now*. Not "we will add monitoring."
- **Post-launch health (data downstream):** where the new data flows on to another store (a reporting copy, an export), name the **downstream watch** for the first days after launch: does new data arrive there, and the query(ies) for **adoption** (accounts or users per day), **empty-state rate**, **error/null rate**, **sanity** (numbers in a plausible range, the wrong-numbers check on real data) and **freshness** (is the copy current). Plus **who watches, how long, and the healthy-vs-investigate threshold**.
- **A new table that a replication or export pipeline should carry.** When capture into a downstream store is opt-in (an allowlist, a publication, a load config), a new table is **not** carried by default, and enrolling it is a deliberate act whose steps fail silently when skipped. Name each step the pipeline needs (for example the table setting the change stream requires for updates and deletes, the capture allowlist, and the downstream load config), and point at the repo's pipeline docs rather than restating them. If the table should stay **out** of the pipeline, the default already does that, but state it, so it is a decision, not an accident.
- **Ground in:** the repo's observability and data-pipeline docs, and any observability skill domain routing finds.
- **Review hook:** prod-facing change with no real-time signal → WARN; a feature whose data flows downstream with no downstream watch → WARN; a **new table the design intends for a replication or export pipeline with no enrollment steps named and no downstream-load decision** → WARN.

## 3. Tenant isolation & access scope
*Applies to every new or changed DB read/write path.*
> State the **intent**, then decide which access dimensions apply: does this **sit within a data-retention or plan window** the product enforces, or not? does processing need **entitlement filtering** (only accounts on a plan that includes the feature), including the **cost angle** (skip expensive work for accounts that are not entitled to it)? Querying is **always** bounded by the tenant-isolation policy (e.g. RLS). A new processor / consumer / flow must decide whether **all, specific, or none** of the access dimensions apply — and justify "none." Use the repo's tenant-scoped data-access helpers for background work too.
- **Ground in:** the repo's tenant-isolation and plan/entitlement docs; any tenant-scoping skill domain routing finds.
- **Review hook:** a new DB path with no tenant-scoping treatment → FAIL; missing plan/entitlement decision where it applies → WARN.

## 4. Scale
*Applies when load or data grows with tenants, time, or usage.*
> Start from **rough client sizing** and extrapolate. Pick the unit that fits *this* RFC — per request, per org, **per processor run**, per event, storage growth, LLM calls — and estimate the load/data at a realistic large client, then **to what scale should this hold** (12 months / 10x). What breaks first — a full scan with no composite index, an unpartitioned time-series table, an unbounded JSONB column, a fan-out join, a vendor rate-limit budget? (Processors are just one example of the unit; the framing is "size it, extrapolate, name the first thing that breaks.")
- **Load-bearing → its own treatment, with figures *and* the mechanism.** When the design stands or falls on scale/fan-out (e.g. many small tenants), it earns a **dedicated treatment**, not a buried sub-bullet: the **figures** (tenant counts, schedule-rows / processing load per run, growth) **and the actual mechanism** that absorbs it — the scheduler batching spelled out with its sizing, the composite index, the partition. A one-line assertion ("a scheduler cohort handles fan-out") is not a treatment; design the v1 mitigation in, don't defer it.
- **A growing table needs a retention decision — an eviction policy *and* its trigger, or an explicit retain-by-design rationale.** When the design adds a table (or JSONB blob) that grows unbounded with usage, either state the eviction **basis** (age/TTL vs LRU / last-accessed vs a size cap) **and the mechanism that triggers eviction** — a scheduled job, or, if eviction stays manual for v1, the **growth alert** that tells an operator to run it — **or** state that the table is retained by design (an append-only audit/event log) and why that is safe at scale. A retention policy with no trigger is a deferred manual script that fires only once the table is already a problem; front-load the trigger, not just the policy. If the eviction relies on a column that ships **unpopulated** for v1 (e.g. a `last_accessed_at` not yet written), state its rationale and future-enable path inline so the reviewer does not have to ask "if it is unpopulated, what is the point?".
- **Aggregate pipeline write volume, not just per-row size.** For a table that flows downstream through a replication or export pipeline — especially a **reusable pattern many callers will adopt** — size the *aggregate* write volume (rows × callers × frequency) against the pipeline, and name the backstop (the pipeline's lag alarms), not only the per-row message size. A "safe because each row is small" claim with only a per-org row gauge and no aggregate ceiling is the acute form of the scale WARN.
- **Review hook:** a system that grows with scale and has no sizing/extrapolation → WARN (fires on any scale-applicable RFC with only a one-liner); when scale is the *primary* risk (the design stands or falls on it), a one-line assertion with no figures/mechanism is the acute form of that WARN — escalate it to the top of the findings. A **growing table with no retention decision at all — neither an eviction policy + automated trigger (or named growth-alert) nor an explicit retain-by-design rationale** → WARN. A **replicated / reusable table sized only per-row with no aggregate write-volume ceiling + backstop** → WARN.

## 5. External / cross-service dependencies
*Applies when the design reads a field an integration may not store, needs a vendor scope, or depends on another service's data.*
> Does this depend on data that may not exist yet — a vendor field the integration doesn't store, an OAuth scope not requested, a column another service owns? **Confirm it against the actual integration code / schema / schema snapshot, not the PRD's assumption.** An unconfirmed dependency is the classic descope-or-block fork: if the field isn't there, do we descope the dependent slice or block on an integration change? Decide now, with the confirming check named.
- **External-vendor auth: enumerate per operation, spike early.** Don't assume a vendor's API is uniform — enumerate the **operations** and the **endpoint + auth** each uses, because per-resource scopes often differ (an org-scoped or admin operation may need a different token type or permission than a repo-scoped one). **Verify each against the vendor's current docs rather than encoding a blanket conclusion** ("a PAT can't do X" is exactly the assumption that goes stale — confirm it per operation). Spike the auth/endpoint assumptions (e.g. App vs classic / fine-grained PAT vs OAuth, plus any org-approval gates) **early — before the LLD hardens** — a vendor-auth limit discovered late forces a redesign.
- **Ground in:** the integration's spec + code, via whichever skills domain routing finds for it (and for any job that reads the field) — this is also where a *new* integration RFC anchors its whole design, not just this dependency check.
- **A read narrowed by a lookup states the lookup's failure return, and the default narrows.** When the design bounds a read by asking something first (which payment providers an account has enabled, its plan, its active stores), that lookup is a dependency with a failure mode, and the reliability question is which way it defaults. Falling back to the union ("assume every provider is enabled") restores exactly the load or scope the narrowing removed, and does it silently: nothing errors, the job just reads everything again. State the failure return and make the default the narrow one (error and retry), so a blip cannot quietly undo the narrowing.
- **Review hook:** an unconfirmed data dependency presented as settled → FAIL; an external-vendor design that assumes uniform auth/endpoints with no per-operation enumeration or early spike → WARN. A **read narrowed behind a lookup with no stated failure return, or one that defaults to the wide set** → WARN (a scope gate that can return unknown fails closed).

## 6. Decision ownership (the whose-call-is-this class)
*Applies when the design introduces or changes a value that shapes behaviour a customer can observe — a threshold, a filter, a classifier vocabulary, a window, a cadence, a default, a scope.*
> **Who is entitled to decide this value, and does the design let them?** Not "is it hardcoded" — a constant is often right.
- **The owner ladder:** **domain** (a fact about the world or a protocol → a literal); **us, uniformly** (same for every customer, changeable without a code change → config); **us, per rollout phase** (→ a feature flag that dies after rollout); **the customer** (the right value differs by customer → a scoped admin setting).
- **The four questions:** **ownership** (who decides and why — "domain fact" needs a stated reason); **reach** (every path that must honour a knob or setting); **default** (what a customer who configures nothing gets — today's behaviour, provably); **legibility** (does an unmeasurable result say "unmeasurable", or render a confident zero?).
- **The four failure modes:** **frozen policy** (a customer-owned decision shipped as a literal); **inert knob** (a setting nothing reads, or one overwritten downstream); **partial reach** (honoured by some read paths and not others); **silent zero** (an unmeasurable result rendered as a real zero).
- **Deferring is a legal answer; deciding silently is not.** The ladder is `literal → recorded candidate → wired knob/setting with a named reach set`. A design that says "customer-owned, deferred to P1, here is why" passes. Record the verdict in the `## Decisions Log`, so the next person inherits the decision rather than re-deriving it — that Log is this concern's output; there is no separate register.
- **Review hook:** a design that introduces a behaviour-shaping value with **no ownership statement at all** → FAIL. A promoted knob/setting with **no enumerated reach set**, or **no named consumer** → FAIL. An ownership verdict of "domain fact" asserted with **no reason** → WARN; a promoted value whose **default is not stated to preserve today's behaviour** → WARN.

## 7. Output quality (the plausible-but-bad-output class)
*Applies when the design's value depends on how **good** its output is, not merely that output was produced — a generated summary, a classification, a detector, a recommendation, a ranking, an extracted entity, a score. The sharp test against concern 1: there, a right answer is **computable** and a fixture can assert it; here the output is **graded**, two careful reviewers can disagree, and a passing integration test proves the pipeline ran and nothing about whether the result is any good. A design that only moves or stores such output — a cache, a transport, a schema change — does not trip this.*

> What is the **quality bar**, how is it **measured**, and what evidence says it is reachable? Front-load these three, because a design that ships the plumbing for a graded output and defers the quality question has proven the pipeline, not the product.

- **State the bar in gradeable terms.** Not "useful summaries" — name the property, the scale, and the threshold, so two people grading the same output land in the same place ("at least 8 of 10 sampled summaries name the actual blocking dependency, judged against the PR thread"). A bar nobody else can apply is not a bar.
- **Name the evaluation method, including its baseline.** How the sample is drawn (a hand-picked demo set flatters; a random draw over real tenants does not), who or what grades it (a human rubric, a gold set, an LLM judge — and for a judge, what establishes its agreement with human labels), and the **baseline** the result is read against: today's behaviour, a deliberately trivial heuristic, or nothing at all. A quality number with no baseline cannot say whether the design helped.
- **Ground the achievability claim in evidence, not in the design's confidence.** If a POC, spike, notebook, or prior run exists, **carry its results into the doc** — the sample size, the measured number, and where the artifact lives — rather than asserting the approach works. If none exists, the quality question is genuinely unsettled, so make a **quality spike an early slice that gates the LLD**, the same posture concern 5 takes on vendor auth and for the same reason: a limit discovered after the schema, the contracts, and the fan-out have hardened around it forces a redesign. Do not build the machinery around an output nobody has looked at yet.
- **Decide what happens to output that misses the bar.** Suppressed, shown with a confidence caveat, retried, or routed somewhere a human can inspect it — and whether the reader can tell the difference. A design that describes only the good case has no failure mode for its own product.
- **Name the ongoing quality watch.** Graded quality drifts as inputs, prompts, models, and tenant mix change, in ways a pipeline metric never shows — the job still runs, the table still fills, the output quietly gets worse. Name the recurring measurement (a periodic re-run of the eval set, a sampled human read, a judge-agreement metric), how often, and the number that triggers a look. This is the quality sibling of concern 2's post-launch health watch.
- **Ground in:** concern 1 above for the computable-answer half; the LLM-service skill domain routing finds, when an LLM produces the output.
- **Review hook:** for a design whose value rests on graded output, the bar and the method are **independent** defects, each → FAIL: **no quality bar**, and — separately — **a bar with no evaluation method or no baseline**. A bar nobody can measure is exactly as unusable as no bar, so grading them as a pair would let "we target useful summaries, method TBD" through the gate. A stated bar whose achievability rests on **neither cited POC/prior evidence nor a quality-spike slice that gates the LLD** → WARN. A **cited POC carried in as a link or a name with no sample size and no measured number** a reader can weigh → WARN. **No stated behaviour for output that misses the bar** → WARN. **No ongoing quality watch** where the output will drift → WARN.
