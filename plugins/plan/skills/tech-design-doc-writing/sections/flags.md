# §10 Feature Flags

**What it is** — the flags that gate this change, with each flag's full lifecycle. This is the inventory + lifecycle, distinct from the §9 phase plan.
**Applies when** — any change that ships behind a gate (most user-facing features).

## Claude drafts (derivable)
- The flag list the design implies (the breakdown table → the warning → the prerequisite, etc.).

## Author decides (grill — printed question + your recommendation + "or your take")
For **each flag**:
- **Name** — a field on the repo's feature-flag config (matches the convention).
- **Default** — usually `false` / fail-closed.
- **First-rollout orgs** — the pilot, as per-org overrides set to on.
- **Ungate criteria (measurable)** — the bar to go from per-org to the global default on. This **is** the GA gate; it consumes the §3 DoD signal (e.g. "4 weeks, error rate < X, zero privacy complaints").
- **Rollback** — flip the override / default; what triggers it.
- **Scope** — org / seat / global; prerequisite flags (does it depend on another being ON?).
- **Gating subject — what is the gate keyed on?** A per-org flag is keyed by the org ID (a per-org override over a global default). If the gating subject has **no org ID at gate-time** — e.g. an email *before* any tenant exists (pre-tenant / identity-keyed gating), or a flow where the org isn't resolved yet — the per-org override model does not apply. Decide the mechanism explicitly (an identity-keyed allowlist, a separate gate); don't force the org-flag shape onto a subject that has no org.
- **A read-source cutover flag has four fixed gates, not generic ungate criteria.** When a flag switches readers from one source of the same facts to another — a JSONB array to its child table, a raw scan to a precomputed rollup — "4 weeks, error rate < X" is the wrong bar, because the failure mode is not an error: readers hit a partially-populated target and every dashboard silently undercounts. So state all four: the **ungate criterion is a row-set-equivalence proof per reader plus an `EXPLAIN` showing the new plan is cheaper** (equivalence tests prove identical results *for the same data*, which is exactly why the backfill precondition matters); the flag **fails closed to the old source**; **dual-write continues until no org can still resolve to the old source**, so that source is never behind — the global default being on is not that point when an explicit per-org off outranks the global default, because a disabled or rolled-back org keeps reading a source that has stopped being written; dual-write ends when the old read path and its negative overrides are retired; and the rollout is **per-org, never fleet-wide**, because a global flip before an org's backfill has reconciled makes that org read an incomplete table.
- **Flag home & delivery — which config declares it, and how it reaches the enforcing code.** A per-org flag is a field on some service's config, and each service usually has its **own** config. Two decisions the flag's shape alone does not settle:
  - **Home — declare it on the config of the service that *enforces* it.** Name the service whose code reads the flag at runtime; that service's config declares it. Reaching into another service's config to read a flag is the same cross-boundary smell as importing another service's internals or data layer — treat it as a boundary even where no arch test enforces it for config — so when the enforcing service differs from the service that owns the feature's data or table, the flag lives with the **enforcer**, not the data owner (a flag the scheduler gates on lives on the scheduler config even if the connector owns the table).
  - **Delivery — how the value reaches the gate.** Name the mechanism that carries the resolved flag from config to the code that branches on it — resolved in the DI wiring, a factory closure, or injected via the task/execution params — and confirm it does not force a cross-service config import to get there.

Use the repo's real flag mechanism — typically a **global default plus per-org overrides**, where an org's override wins over the default and an unset flag is fail-closed. Rollout progression: default OFF + pilot orgs overridden ON → widen → default ON. (Read its source for the exact shape; don't restate it here.)

**Exception — an identity-keyed / pre-tenant gate** (the gating-subject case above): the per-org flag object and its first-rollout-orgs / per-org-then-global progression **do not apply**. Define the *equivalent* lifecycle on the identity instead — an allowlist (or a separate gate) with its own **measurable ungate criteria + rollback**. That is a deliberate, designed alternative; the "use the real flag mechanism" expectation is satisfied by naming this explicit mechanism, not by forcing the org-flag shape onto a subject that has no org.

**Exception — a global per-surface config lever** (not a per-org flag at all): some correctness / data-refresh changes roll out via a **global config value that is not keyed by org** : for example a client-wide "refresh your cache" counter in a service's config, gated only by app version. Bumping it makes **every client** refetch, so there is **no per-org targeting** — a "pilot just these orgs" plan the org-flag model assumes is impossible with this lever. When the rollout mechanism is a lever like this, say so explicitly and state its **scope granularity** (global / per client type / per surface) and do **not** describe a per-org phased rollout the lever cannot deliver. State its rollback **honestly for the lever's actual semantics** — a monotonic served counter is effectively **irreversible** once clients consume a bump (lowering it is a no-op for caught-up clients and can re-trigger a fleet-wide storm or defeat the very fix, per the surface's own ops runbook), so its "rollback" is a **forward corrective** (a fresh gated bump / a runbook recovery), never a decrement. Do not prescribe "just revert the counter" for a lever that cannot honor it. This is the same shape as the identity-keyed carve-out (the org-flag model does not fit), a different cause (a global config lever, not a pre-tenant identity).

## Ground in (pointers — read, don't restate)
- the repo's feature-flag type (its default/override resolution) and its config wiring; the config skill domain routing finds, if any, for the flag-wiring slice
- the per-service config packages and the DI wiring — for the flag-home + delivery decision (which service's config declares it, how it reaches the gate)

## Review hooks (what /plan:tech-design-doc-review checks here)
- Each flag has **default + measurable ungate criteria + rollback** → missing ungate criteria → FAIL (a flag that ships suppressed forever).
- The flag is expressed via the repo's real per-org-then-global flag mechanism → an ad-hoc bool with no rollout path → WARN. **Exception:** a *deliberately-chosen* identity-keyed / pre-tenant gate, **or** a *global per-surface config lever* (e.g. a client-wide cache-refresh counter) — is a designed alternative, **not** an ad-hoc bool. The global-lever exception is **evidence-bound, not self-attested**: it clears the WARN only when the design cites the lever's **real config field + enforcing code path + persisted-state semantics + authoritative ops runbook**, and states why the change cannot target more narrowly. A bare global bool merely *labelled* "config lever" with no such grounding is exactly the ad-hoc bool this WARN catches — keep flagging it.
- A flag whose **gating subject has no org ID at gate-time**, modelled as a per-org override anyway (the org-flag shape forced onto a pre-tenant / identity-keyed subject) → WARN. (The passing path is the explicit identity-keyed mechanism above — so this WARN and the ad-hoc-bool WARN are not a no-win: one valid answer clears both.)
- **Read-source cutover flag** — a flag that switches readers between two sources of the same facts whose ungate criterion is **not** a per-reader row-set-equivalence proof plus a cheaper-plan `EXPLAIN`, or which is planned to flip **fleet-wide** rather than per org, or which does not fail closed to the old source, or under which dual-write stops while any org can still resolve to the old source (the global default being on is not that point — a negative per-org override outlives it) → WARN. (Generic ungate criteria pass the FAIL hook above and still miss this: the failure mode is silently wrong numbers, not errors.)
- **Flag home & delivery named** — the flag is declared on the config of the service that **enforces** it (not the data owner, if they differ) and the design does not reach across services to read it; the delivery mechanism (DI wiring / factory / execution-params) is stated → a flag homed on a non-enforcing service's config, reached via a cross-service config import, or with no delivery mechanism named → WARN.
