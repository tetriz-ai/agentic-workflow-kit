# §4 High-Level Architecture (HLD)

**What it is** — where the change lives in the system, how it executes, and what it touches. A reviewer should grasp 80% of the design from the diagram.
**Applies when** — every feature RFC. A pure refactor may shrink it to "no architecture change."

## Claude drafts (derivable)
- **One diagram** showing components, data flow (what data moves, not just arrows), the tables written, and the owning service per box. No decision rationale inside the diagram. This is the doc's **one** high-level diagram — the overall end-to-end flow; the sections above (Terminology, Problem, Goals) stay **prose**, and per-flow sequence diagrams, DDL, and API examples belong in §6 LLD, not here.
  - **Format — pick by diagram type and render surface (and the author's preference):**
    - **ASCII swimlane** (lanes + arrows) for wide / multi-actor **sequence** diagrams and anything with long labels — it reads best and renders at full size everywhere. Don't use a textual `A → B: msg` list for these (harder to follow), and don't reach for the generators: Mermaid and PlantUML `-tutxt` both inflate width and shrink fonts on wide / many-actor sequences (Mermaid's whitespace also grows with the participant count, and GitHub strips the `fontSize`/`useMaxWidth` config that would tune it), so neither beats hand-ASCII here. Accept the alignment upkeep — align the trailing lane bars to one column.
    - **Mermaid** for compact flowcharts / component graphs (a handful of nodes, short labels): clean on GitHub, diffs semantically, parses well for agents — and at small size the shrink/whitespace problems don't bite.
    - Tiny sketches: either. Keep any diagram conceptual — no implementation detail in the picture.
  - **Composition — number the parts, order them as the data flows, and say in one sentence how they join.** This applies when the figure has two or more **independently-rooted** subgraphs with no arrow between them (a write path, a settings/control plane, a read path drawn side by side); a single connected flow needs none of it. Number each part in flow order (`1 write` → `2 settings` → `3 read`), lay them out so the figure reads top to bottom in that order, and put **one sentence directly under the figure** saying how the parts compose. Three correct planes drawn side by side with no numbering and no composition sentence is the shape that draws "this is not well structured" from a first reader.

## Author decides (grill — printed question + your recommendation + "or your take")
The author must reason about the *whole* system, not just the happy path. Raise the ones that apply:
- **Owning service** — which service (or module) owns the new work, and why.
- **Execution model** — sync request/response, or async (a queue consumer, or a scheduled job)?
- **Queue/event** — reuse an existing queue/topic, or add a new one?
- **Trigger and granularity — what fires the work, and how much it processes per firing.** *Raise this whenever the design processes data that arrives over time: a consumer, a processor, a sync, a recompute, a scheduled job. A purely synchronous read path does not trip it. Reusing an existing queue settles only **what fires the work** — a new consumer on an existing queue inherits that event source and nothing else, so it still owns its own granularity, idempotency, backfill and tenant fan-out. Answer the trigger question in one line there, but the four consequences below are only skippable when the **existing implementation path** the change reuses already provides them, which is a claim about that code, not about the queue.* The two ends are **per item as it arrives**, which is freshest but pays the full per-firing cost on every item and fans out hardest, and a **periodic sweep over a window**, which is cheapest per item but leaves the output as stale as the interval; a **micro-batch** sits between them. State which you chose and the trade you accepted. Then answer the four things that follow from the choice, because each is a defect if left implicit: what happens to items that **arrive mid-run**; how a **re-delivery or a replay** stays idempotent *at the granularity you picked* (per-item idempotency does not survive being re-batched); whether a **backfill** reuses this same path or needs its own; and how the fan-out **staggers across tenants** so a sweep does not thunder. The freshness §3 or the PRD asks for and the load §7's scale concern sizes are two constraints this one decision has to satisfy at once — reconcile it against both rather than picking on habit.
  - **Cadence arithmetic, for a scheduled fan-out.** A per-org schedule is spread across the phases its expression has — the step for `*/n`, 60 for hourly — so the cohort firing in one minute is roughly *orgs ÷ phases*, and phase 0 of every family lands on :00 whatever the hash does. State that number, not just the interval. `* * * * *` has one phase and therefore **cannot** be staggered: choosing per-minute means choosing a fleet-synchronised firing, so it needs a freshness target that demands it. Operations sharing a rate-limit bucket have to share a phase group, since a limiter caps a window's count without spacing requests inside it. And name the **metric that will show whether the schedule behaves as designed** here — a schedule shipped without one cannot be shown to behave.
- **Processors** — do they chain / waterfall; how do multiple stay in harmony (ordering, idempotency, reprocessing)?
- **External API calls** — do they go through the repo's shared outbound client, so retries / rate-limit / circuit-breaker apply?
- **Which DB + tables** — which database, new vs existing tables, time-series partitioning?
- **Downstream data** — does new data need to flow on to another store (a reporting copy, an export)? (ties to the Observability concern's downstream watch.)
- **Deployment** — reuse an existing deployment, or a new pod / cron? (The repo's standard deploy *mechanics* stay out of the RFC **unless a new infra component is added**, in which case describe it here.)
- **The independent moving parts** a feature forgets — the scheduler, other consumers, identity resolution, plan/entitlement gating, caching, rate-limit scope.
- **Reuse vs new** — for each piece, are we extending an existing component or adding one, and why.

## Review hooks (what /plan:tech-design-doc-review checks here)
- A diagram is present and shows **data**, owning services, and the tables written → missing/blurry → WARN.
- A figure with **two or more independently-rooted subgraphs sharing no arrow between them** has its parts **numbered in flow order** and a **composition sentence** under it → neither present → WARN. (A single connected write→store→read flow does not trip this; the target is parts that read as disconnected.)
- Code blocks are concentrated at this layer (the one overall diagram) and in §6 LLD; the sections above HLD are prose → a diagram / DDL / API block placed above HLD → WARN.
- The execution model (sync/async, queue reuse-vs-new) is stated for any data-moving feature → WARN if silent.
- **Trigger and granularity** stated for any design that processes data arriving over time — what fires the work, how much it handles per firing, and the trade accepted → silent → WARN. A stated trigger that leaves all four consequences implicit (mid-run arrivals, idempotency at that granularity, backfill reuse, tenant staggering) → WARN.
- **The trigger contradicts the doc's own numbers** → WARN. This is the cross-check, and the more valuable half of the hook: per-item firing on a fan-out §7 sizes as heavy, or a sweep interval longer than the freshness §3 or the PRD asks for. An unreconciled choice is the failure — not the absence of a paragraph. When the reconciliation **cannot be made** because §3 states no freshness target or §7 sizes no fan-out, that is also a WARN, not a pass: the doc most likely to get its trigger wrong is the one with numbers on neither side, and silence there would read as clean.
- **Cadence arithmetic** for a scheduled per-org fan-out (each a WARN) — a cadence stated as an interval with **no cohort arithmetic** (orgs ÷ phases, and what coincides on phase 0), so the doc names a frequency but never the load; a **per-minute** cadence with no freshness target that demands it (it is unstaggerable, so it is a fleet-wide simultaneous firing by construction); and a **per-org firing whose first read is fleet-wide** — a job that fires once per org and then scans every org's rows pays the fleet on every tick.
- **Reuse-vs-new** is justified, not defaulted; the independent moving parts are addressed where relevant.
- A **new infra component** (pod / queue / topic / cron) is called out explicitly → silent new infra → WARN.
