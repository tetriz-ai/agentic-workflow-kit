# §6 Detailed Design (LLD)

**What it is** — the contracts, the data model, the processing, and **how the change distributes across the codebase**. Nails the decisions that are expensive to change later.
**Applies when** — every feature RFC.

## Claude drafts (derivable)
- **API Contract** — proto/HTTP specs; write **three example calls a real consumer makes** before the spec; concrete request/response, not just types.
- **Data Model** — SQL DDL as source of truth; start from **access patterns**, not entities; per-index "which query it serves"; expected row count + growth.
- **Sequence diagrams** — one per user-facing flow, showing the data.
- **Processing logic** — data flow source → service → target; not step-by-step code.
- A first cut of the **package/code-distribution** table.

## Author decides (grill — printed question + your recommendation + "or your take")
The recurring things RFC reviewers flag — front-load them here:
- **Write the LLD prose for a cold reader (this is the densest section, so the biggest cold-read offender).** State the mental model before the mechanism, define each term at first use, bullet a multi-claim paragraph and table a multi-row correspondence (operation→cache, type→shape) — per the structure rules in [rfc-readability-rubric.md](../rfc-readability-rubric.md). Grammatically-clean prose a fresh reader still cannot restate is the failure this catches.
- **Package/code-distribution table** — where the new packages/files land in the codebase (Claude proposes, *you* confirm). A table: new package/file → what lives there → which service. If the design ships a per-org feature flag, its **config home** (which service's config declares it) and **delivery** are part of this distribution decision — see `sections/flags.md` "Flag home & delivery".
- **Mechanism forks — decide the *how*, don't narrate it.** When the design asserts *how* something works and the "how" genuinely forked, each is a Decisions Log row (or `UNRESOLVED`), never a confident sentence. Typical shapes: a derived helper/method vs a stored column; which component owns a state transition, and how a capability is turned off for a variant; how a fan-out is batched and how it interacts with existing per-entity overrides; how identities are auto-linked when the join key is ambiguous. A mechanism smoothed into prose is a silently-resolved fork.
- **Namespacing by domain** — name enums/protos/packages so future siblings slot in (e.g. `billing/refunds/`), not a name that collides when a second use-case arrives. A **generic type name in a shared package** (`common.v1.DeviationState`) is ambiguous given where it lives — a type in `common.v1` needs a **domain prefix** so its meaning is clear at the use site.
- **Naming is a fork** — a load-bearing discriminator like `accounts.type` and its enum values deserve a *named* Decisions Log decision, not a silent default.
- **Index per query** — for each query: access pattern (point / range / JSONB-containment / FTS) → the index (btree / composite / GIN path), and the **scale milestone** where offset-pagination must become keyset. Three more things per query, because they decide the cost and are cheap to state now and expensive to retrofit:
  - **Which columns the query binds** — the tenant column named explicitly in the `WHERE` (the RLS policy is a per-row filter, not an index boundary), and, on a partitioned table, the **partition column itself bounded** (a correlated timestamp prunes nothing) — state *both* bounds, or justify the missing floor where a floor would change the result set (filtering `orders.created_at` to the reporting window drops an order created earlier and fulfilled inside it), which is a per-caller call rather than a blanket one. The index then has to lead on those bound columns before the sort tuple.
  - **The call rate** — per request, per event, per org-tick, per day. Row count × call rate is the load; a per-query row estimate on its own does not size anything, and the same read is cheap on an admin path and the top DB consumer inside a queue consumer.
  - **How a key set is passed** — a data-dependent id/key set binds as one array parameter, never expanded into one bind per element (per-element binds defeat the plan cache and hit the driver's parameter cap — 65,535 in Postgres).
- **Write pattern** — last-write-wins / append-only / incremental-assembly; for incremental, every upsert preserves existing values (no partial-write blanking).
- **Proto enum / typed proto for JSONB** — enum-like values use a proto enum, and `jsonb` uses a proto message, not `map[string]any`/`[]byte`, + `sql.Scanner/Valuer`.
- **Schema modeling — the type choices reviewers keep making by hand.** Beyond the JSONB/enum rule above, decide each of these *before* the DDL sets (they recur across RFCs because the AI author defaults them wrong, so grill them and gate them):
  - **A proto enum, not a bare integer, for an enum-like column.** A status/state/kind column stored as a bare `int`/`smallint` — even one carrying a `-- SomeEnum` comment — loses meaning and safety, and is not readable at the table level. The correct pattern is a proto-enum-typed model field whose generated `sql.Scanner`/`Valuer` stores the **proto name string** (`"ORDER_STATUS_SHIPPED"`) in a `text`/`varchar` column — human-readable in the DB; the antipattern is the bare integer, or a comment-only pseudo-enum, with no proto enum behind it.
  - **Boolean that should be an enum.** A boolean state column whose state space could plausibly grow (`is_active` when a third state is coming) → prefer an enum now; a bool is a one-way door.
  - **Reuse an existing type before defining a new one.** Grep the protos / codebase for an enum that already models this before minting a new one — a duplicate (a second order-status enum when one exists) fragments the model.
  - **Enum dimension / granularity / zero-value + catch-all.** One dimension per enum; **consistent granularity** (don't mix vendor-specific values like one vendor's product name with generic ones in one enum, and don't mislabel a value as vendor-specific when it applies broadly); the zero value is `*_UNSPECIFIED` (the buf `STANDARD` lint convention — not `*_UNKNOWN`); and add a distinct **nonzero** `*_OTHER` member only when the design must capture an unmapped-but-known-other value rather than drop it (an `OTHER` bucket is not the default — unset/unknown semantics stay `*_UNSPECIFIED`).
  - **Column vs. JSONB consolidation.** A field you will *not* filter or sort on doesn't earn a top-level column — consolidate the non-queried fields into a typed JSONB blob; promote to a column only what a query keys on.
  - **How many tables, and which collapse did you reject?** State the count you chose and name the specific alternative you did *not* take, with the reason. "One more table" is the cheap local choice and the expensive global one, so the rejected collapse is the part worth writing down; when the choice is load-bearing it earns a Decisions Log row. The catalog of collapses to consider — and the inverse guard against answering this by collapsing everything into one wide table — is `/review:review-panel`'s opt-in `database-migrations` lens (review-lenses plugin), which reviews the same question on the migration; do not restate it here.
  - **Growth class per new table** — bounded / per-org / per-person / per-event / per-day — and, for a per-event or per-day table, the retention or partitioning answer. This is the §7 scale concern applied per table rather than per flow; a table with no growth class stated has not been sized.
- **New-table columns justified against the same-DB siblings.** For a new table, justify the org/tenant **key type** (why `varchar` vs `uuid`) and the **audit columns** (`created_at`/`updated_at`) against the sibling tables in the *same* database : for example every table in one database may key on an `account_id` of one type with the same row-level-security expression (a *consistent* idiom), while the audit columns **vary** (one table carries `created_at`, another does not), which is exactly why you justify your table's choice against them rather than assume. A deliberate divergence from a *consistent* sibling idiom (the key type and its row-level-security expression) needs a Decisions Log row (it otherwise breaks RLS-idiom consistency and cast-free joins).
- **Ownership / wiring claims are grounded, not derived.** Any statement about service / DB / package ownership or wiring location ("X owns the DAOs", "Y has no DB of its own", "wired under Z") is verified against the actual DI wiring, data-access code, and package layout **before you write it**, not inferred from the design's own logic — see the rubric's *Grounding* item for the worked instance (the library-vs-owning-service distinction).
- **Formula-vs-artifact agreement (write-time self-check).** When a subsection states an invariant/formula (a settings-write rule like "write iff DualWrite AND NOT Read") **and** also shows pseudocode or a phase/transition table for the same behaviour, verify the two **agree before moving on** — a stated formula that contradicts its own pseudocode/table is a silent trap the implementer inherits. (The review skill's intra-section-contract check is the backstop; the point of this prompt is to catch it at write time, not at review.)
- **Widening a shared set or definition — state the rule at every scoped grain, not just the org total.** When the design widens something more than one surface reads (an attributed-key set, a metric population, an eligibility filter), the org-level rule is the easy half. Each **scoped** grain — per person, per team, per project, per language, a matrix cell — is typically resolved on a *different join key* than the org's (the order's placer vs the account it bills), so an org-only rule silently breaks either the scoped views or that grain's reconciliation invariant, and which one breaks is an implementation accident rather than a decision. Write a per-grain table (grain → does it widen → on which key → what the reader sees) and name the fixture that proves the invariant still holds — but **first answer, per grain, whether one item lands in exactly one row of it, and read that off the fan-out code rather than inferring it from the entity relationship one hop up.** Only a genuinely one-row-per-item grain sums back to the org total; for the rest, fixture that each item reaches exactly the rows it should and that any coverage gap stays visible, because asserting a sum there encodes a falsehood. **Team is the trap worth knowing:** every order has exactly one placer, so per-team reads like a partition, yet a person belongs to several teams, and a per-team fan-out counts that person's order in each of them. The one-placer fact is true and settles nothing. Worked instance: a design widened which orders count as discounted. At account level the rule was one line. Per team it was not: a buyer places one order that combines two colleagues' requests, the colleagues sit on different teams, and the order counts in the buyer's team while the colleagues see their requests only through the drill-down.
- **Concurrency & idempotency** — list the concurrent edge cases (two admins, periodic job + force-job, consumer-lag + reprocess) and the safety (row/advisory lock, compare-and-swap, idempotent-apply, a state machine). Single TX is rarely enough.
- **Error handling** — per path: recoverable or terminal? soft failure (missing optional data, timeout) = empty signal vs hard error? what does ops see?
- **Backward compatibility** (folded here) — is the schema/API change **additive or breaking**? Breaking → the migration/shim + old-client (desktop / cached web) + in-flight-during-cutover handling.
- **Tunable in config vs code constant** — anything ops may need to tune per-env (timeouts, batch sizes, lists) → the repo's config system, with a default + safety bound.

## Ground in (pointers — read, don't restate)

- the **build skill for what this RFC ships** — find it with the SKILL.md domain-routing step (the session's skills and the repo's own `.claude/skills/`) and read it before drafting the data model + contracts

## Review hooks (what /plan:tech-design-doc-review checks here)
- **Package/code-distribution table present** for a multi-file change → missing → WARN.
- **Index per query** + a keyset milestone for any growing table → missing index for a stated query → WARN.
- **Read cost stated per read** (each a WARN) — a new read with **no call rate** (per request / event / org-tick / day), so its row estimate sizes nothing; a cron or consumer the RFC adds with **no read-cost line for its first query**, even when it introduces no new table (the hooks above key on tables and stated queries, so this is the only thing that catches it); a read on a **partitioned table that bounds only a non-partition timestamp**, which prunes nothing; and a read on a partitioned table with **no stated position on the partition floor** — either both bounds, or a named reason the floor is declined because it would drop in-window rows (the absence of a floor on such a caller is not itself the finding).
- **Stable IDs in keys** (no mutable names in uniqueness constraints) → FAIL.
- **Write pattern stated**; **partial-write safety** on insert-or-update → unsafe → FAIL.
- **JSONB uses typed proto / enums proto-typed** → string-in-JSONB enum → WARN.
- **Concurrency safety** named for any write RPC / async transition that can race → silent race → WARN.
- **Mechanism stated as prose with no Decisions Log row** — a load-bearing "how" the design depends on, asserted confidently but never decided → WARN (a silently-resolved mechanism fork).
- **A load-bearing discriminator / enum** (e.g. an `accounts.type`-style column) introduced as a silent default with no Decisions Log row → WARN (naming is a fork).
- **Schema modeling** (the recurring cross-RFC misses; each a WARN) — an enum-like **scalar column** stored as a bare `int`/`smallint` with no proto enum behind it, even one with a `-- SomeEnum` comment (the correct pattern is a proto-enum-typed field serialized as the proto **name string** into a `text`/`varchar` column via Scanner/Valuer — do not WARN on that; the in-JSONB case is the proto-typed-JSONB hook above); a boolean whose state space could grow (should be an enum); a new enum that duplicates an existing one; an enum mixing granularity (vendor-specific + generic in one dimension), a zero value that is not `*_UNSPECIFIED`, or a design that drops unmapped values where a nonzero `*_OTHER` is needed; a generic type name in a shared package with no domain prefix; a narrow single-metric table with no justification.
- **Table count + growth class + denormalization ownership** (each a WARN) — a design adding tables with **no stated count decision and no rejected collapse** named; a new table with **no growth class**; a growth class stated but **no first-break-at-10x** named (the class alone is not the analysis — `per-org` with no hot-row / fan-out / size failure identified is an unsized table); a per-event / per-day table with no retention or partitioning answer; and a **denormalized copy of a value owned elsewhere** — especially cross-DB — missing **either** the read path that justifies avoiding the hop **or** what reconciles it when the source changes (one without the other still drifts). Also WARN the inverse: a new **wide** table whose column groups are mutually exclusive per row (a collapse taken too far). This section is the **only** design-time backstop for these — a routed design doc gets `/plan:tech-design-doc-review` with the other Step 2 lenses suppressed, so anything omitted here is not caught until the DDL exists. The code-review counterpart is `/review:review-panel`'s **database-migrations** lens; keep the two in step.
- **New-table columns vs same-DB siblings** — a new-table key-column type or RLS idiom (org_id type, the RLS cast) or audit-column choice (`created_at`) that diverges from the sibling tables in the same DB with **no Decisions Log row** → WARN.
- **Ownership / wiring claim grounded** — a service / DB / package ownership or wiring claim not grounded against the actual DI wiring, data-access code, and package layout → WARN.
- **Scoped-grain widening** — a design that widens a shared set/definition but states the rule only at the org level, with no per-grain table or no named invariant fixture → WARN.
- **Named-actor worked example** — a rule spanning multiple actors, scopes, or a lifecycle stated only in its general form, with no walkthrough naming the entities → WARN (the rubric's cold-read item, applied where this section's rules are densest).
- **A topology or flow decision resting on a structure the doc never draws** — a Decisions Log row or LLD passage whose rationale leans on a branch shape, a fan-out, or a component topology that appears nowhere as a figure → WARN. The reader is being asked to rebuild the picture the decision was made against. (This is the doc-visible half of the diagram-before-the-question norm in the writing SKILL.md; whether the fork was *asked* that way leaves no trace in the doc and is deliberately not graded.)
- **Back-compat** stated additive-or-breaking; breaking with no migration/shim → FAIL.
