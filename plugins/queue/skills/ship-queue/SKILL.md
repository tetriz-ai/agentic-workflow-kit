# Skill: ship-queue

Drain a queue of **already-triaged, author-approved** GitHub issues, fixing them one at a time and opening **one PR per issue**. The approval to *work* the queue happened upstream (the queue label is that handoff — an operator points this skill at it deliberately), so the skill runs **autonomously between gates**: it does not pause for hand-holding per issue. The binding gate is unchanged and human-held — **this skill opens PRs and never invokes a merge; a human reviews and merges.** Every fix passes the merge gate (the deterministic gate) and the review panel before its PR opens. Permission rules that deny the common merge paths (`gh pr merge`, the `gh api .../pulls/N/merge` endpoint, direct pushes to the base branch) are defense-in-depth — but treat them as a backstop, not airtight enforcement (permission globs cannot catch every spelling). The real control is that the loop's *job* is to produce PRs, and merging stays a human action after review.

**It does not stall the queue.** A per-issue blocker (the types are enumerated once, in [blocker-protocol.md](blocker-protocol.md) — do not re-list them here) does **not** stop the run — the loop records a structured marker on that issue, sets it `Blocked`, and moves to the next item (Step 5). It stops the **whole** run only on a queue-wide failure (auth/token expiry, lock contention, a usage pause).

It composes the kit's shippers — `/queue:ship-task`, `/ship:pr`, the merge gate, `/review:review-panel`, `/ship:codex-sweep`, `/ship:github-issues` — never personal skills, so it works for anyone who installs the kit.

**Settings this skill reads** (resolve once, reuse everywhere below):

```bash
CFG="${CLAUDE_PLUGIN_ROOT}/scripts/kit-config.sh"
BASE=$("$CFG" get base_branch '${user_config.base_branch}')
REPO=$("$CFG" get repo_slug '${user_config.repo_slug}')
[ -n "$REPO" ] || REPO=$(gh repo view --json nameWithOwner --jq .nameWithOwner)
QUEUE_LABEL=$("$CFG" get queue_label '${user_config.queue_label}')
GATE=$("$CFG" get merge_gate '${user_config.merge_gate}')
PROJECT=$("$CFG" get github_project '${user_config.github_project}')
```

`GATE` is the command or label that clears the merge gate; blank means the base branch's required GitHub checks. Board steps (setting Status, reading Priority or Estimate) run only when `PROJECT` names a GitHub Project; with it blank they are skipped.

## Ways to run (front door)

On a **bare `/queue:ship-queue`** (or `--options`), do **not** silently start draining — first present these run modes and let the operator pick. A trailing issue-number list, `--resume`, or a command line that already pins the mode (`--list` / `--integration-branch` / `--from-rfc` / a strategy) skips the menu.

| # | Mode | What it does | Command |
|---|------|--------------|---------|
| 1 | **Drain my queue** (default) | Work my assigned `$QUEUE_LABEL` issues one at a time, one PR each (Step 1 onward). | `/queue:ship-queue` |
| 2 | **Show my tickets** (tabular, read-only) | A table of my assigned queue to decide what to pick — **no work is done**. | `/queue:ship-queue --list` |
| 3 | **Drain an RFC breakdown** | Dependency-ordered onto one integration branch (see the integration-branch drain). | `/queue:ship-queue --integration-branch <name>` / `--from-rfc <path>` |
| 4 | **Run specific issues** | Exactly the numbers given, in that order (`pick-list`). | `/queue:ship-queue <numbers…>` |
| 5 | **Continue in-flight PRs** | Take my open/in-progress work *toward merge* instead of skipping it — assess what each PR needs (draft→ready, behind→update, merge gate not green→run it, gate not triggered→apply its trigger) and advance to **merge-ready** (never merges — that stays the human's step); ask the author when a PR needs judgment. | `/queue:ship-queue --continue [issue numbers…]` |

**`--continue` (mode 5)** is the loop-closer for the session-start nudge's "finish first": one command drives the in-flight set to merge-ready rather than the operator hand-running `gh` per PR. Full contract — selection, the assess→advance matrix, the ask-the-author rule, and why it stops at merge — in **[continue-mode.md](continue-mode.md)**.

**`--list` (mode 2) is a read-only view — it renders [`scripts/queue-view.sh`](scripts/queue-view.sh) and stops.** That script is the **single source shared with the session-start ship-queue nudge** (so the two never drift) — see its header for the exact TSV columns it emits. Render them newest-first as a markdown table with columns **Issue (link) · Title · PR · Status · Priority · Created**:

```bash
# my assigned open queue (all ages); override ASSIGNEE/DAYS as needed
REPO="$REPO" LABEL="$QUEUE_LABEL" bash "${CLAUDE_PLUGIN_ROOT}/skills/ship-queue/scripts/queue-view.sh"
```

`queue-view.sh` is **assignee-scoped** (the owner who should work it) and adds Priority/open-PR that the Step-1 in-flow table below does not — reuse it for `--list` and the nudge; the Step-1 selection table keeps its own fetch because the strategy picker also needs the `labels`/`Estimate` columns queue-view omits.

> **A session-start nudge surfaces each person's queue automatically** at the top of every new session (the same `queue-view.sh` data, refreshed in the background — `"${CLAUDE_PLUGIN_ROOT}/scripts/session-start.d/ship-queue-nudge.sh"`): their open queue, the in-flight items not taken to completion, and any `bug-hunt` finding not yet queued (an open decision). Silence it with the opt-out variable named in that script's header.

## The execution model — read this first

The during-coding harness — the commit gate, `self-check`, the **review-cadence** nudge, `pr-nudge`, and the **review panel** they trigger (whichever of the kit's plugins are installed) — fires on **main-loop tool calls only** (plugin hooks). A subagent's internal edits/commits do **not** re-fire them. Therefore:

> **Hybrid per issue: subagents do the heavy cognition, the main loop does the cheap write path.**
> A subagent does the read-heavy grounding (issue + RFC + code → an implementation brief) so it does not bloat the main context. The **write path** — edits, `git commit`, `gh pr create` — runs in the **main loop**, so the commit gate and self-check run, the review cadence counts the commits, and the panel + codex-sweep fire.

The split is by **cost + trigger**, and it is the token-isolation invariant:

- **Cheap trigger-calls stay in the main loop** — `git commit`, `gh pr create`, the edits applying a fix. These re-fire the hooks; that is what arms the panel and the codex-sweep.
- **Deterministic gates run as a zero-token background Bash — not an LLM subagent.** The merge gate is a *deterministic* gate, not cognition: when it is a command, run it as a **background Bash** task whose full log stays on disk, and read only its compact verdict. So run it that way (Step 6) — the multi-minute wait then costs **zero** model tokens, and the main loop reads only the verdict. Wrapping that verdict in an LLM subagent burns a whole turn to relay a deterministic result; that shape is wrong. The same holds for the review-only Step 2.6 cross-model lens engines (the automatic counterpart and OCR, per the registry read at run time) — background Bash calls, never relay subagents.
- **Genuine cognition runs in subagents that return verdict-only** — grounding, the review-panel lenses, any fix-scout. A **red** merge gate is the one gate case that needs cognition (to *fix*): the fix is main-loop or a `fix-scout` subagent (Step 3 "Fix ownership"), never the green-path relay. **Never run build/test in the main loop** as raw commands — go through the merge gate command (background Bash) or a subagent.

The durable state lives **on disk**, not in the token window: a run-ledger plus the GitHub markers (see [run-ledger.md](run-ledger.md)). So after a compaction the loop reconstructs from ledger + GitHub, never from in-context memory.

> **The ledger is a cache, not the authority — ground truth is git + GitHub.** A long unattended drain *will* be compacted mid-run, and a ledger written before a crash can be stale or wrong. So the durable artefacts are deliberately **strong and self-describing** (issue-keyed brief / panel dirs / worktree names, and for an integration drain the per-slice **merge-commit SHA** recorded in the row) — every claim a row makes is re-checkable against git reachability + the GitHub API, by number alone. And the loop **self-verifies**: on every resume (and before the final integration→base-branch PR) a **fresh unbiased subagent re-derives the run state from git + GitHub *without reading the ledger first*, then diffs its finding against the ledger; on any divergence ground truth wins and the ledger is corrected** (Step 6.5 / [run-ledger.md](run-ledger.md) "self-verification"). Never advance a wave on an unverified "done".

## Step 0 — Persistence, ledger, usage backstop

1. **Lock persistence** with `/goal` (built-in; sets a session-scoped Stop hook) — this keeps the **loop alive** to a finished queue; it does **not** gate per-issue quality (the ledger does that). If your harness lacks it, the loop below still drives the work — persistence is then best-effort.
   > `/goal drain the <queue-label> queue (scope: <author>) one issue at a time, marking blockers and moving on, until none remain open or blocked-unresolved`
2. **Init the run-ledger** `.claude/triage/run-<label>-<run-scope>.md` — **`<run-scope>` is the owning Claude session, `<YYYY-MM-DD>-<session-id>` (`$CLAUDE_CODE_SESSION_ID`)** — so the ledger is unique per session and parallel worktree sessions never share a file, for **every** run type (pick-list, `--integration-branch`, full drain, interactive pick) with no per-type encoding, hashing, or deferral. (Session scoping makes the *ledger* collision-free even for two same-label full drains; it does **not** stop them double-processing the same issues — there is no concurrency lock — so don't run two same-label full drains at once.) Full naming + the resume rule: [run-ledger.md](run-ledger.md). One row per issue (`issue → PR# → gate → panel → codex → blocker → status`). This + the GitHub markers are the durable recovery state; the main loop holds only this. **Write a `# resume-cmd: /queue:ship-queue --resume --session <session-id> <this run's exact args>` line into the ledger header** — the exact command a fresh session re-enters with; it **must carry `--session <session-id>`** (the *original* run's), since a resuming session has a different `$CLAUDE_CODE_SESSION_ID` and cannot otherwise locate this ledger. Full schema, the `done` flip rule, the **`## carry-forwards`** table (per-slice must-include / must-verify a later slice owes), and the reconstruct-after-compaction procedure: **[run-ledger.md](run-ledger.md)**.
   - **The mid-run narrative survives compaction because it lives in the ledger.** The `# resume-cmd:` line plus the `## operator-directives` / `## cross-slice re-scopes` / `## carry-forwards` sections are a plain file that outlives a context compaction (which compresses the conversation, not the filesystem) — keep them accurate and a resume reads them straight from the ledger, no hand-written resume-prompt (run-ledger.md "Compaction survival").
3. **Arm the dead-man cron** (the usage backstop) — read `"${CLAUDE_PLUGIN_ROOT}/scripts/usage-guard.sh" resets-at`; if it returns an epoch, `CronCreate(durable:true, recurring:false, cron = <resets_at + 10min, in local time>, prompt = "/queue:ship-queue --resume --session <session-id> <same args>")`. **`<session-id>` is always the id recorded in this ledger's `# resume-cmd:` header (the *original* run's id) — never the current session's `$CLAUDE_CODE_SESSION_ID`.** At the first arm they are equal; but after a resume they diverge (the resuming session has a new id), so a re-arm that grabbed the current session's id would point the next cron at a ledger name that never existed. Every cron/resume-cmd this run ever emits mirrors the header's `--session`. Re-arm whenever the active 5h block rolls; `CronDelete` it when the queue drains.
   > **EXPERIMENTAL — not hardened.** The cron lifecycle and the usage signal it depends on are unfinished. Do not rely on this for an unattended overnight run. **Bound any overnight run with `--limit N` instead** (Step 1) and run attended.

## Step 1 — Build the queue (scoped)

Resolve the invoker and **scope to the issues assigned to them by default** — the queue label is shared, so an unscoped pull would grab teammates' issues. **Assignee, not author, is the default scope**, and it is load-bearing: `/queue:bug-hunt` is run by one person who files findings and **assigns owners to teammates**, so the person who should *drain* a ticket is its **assignee**. This must match the `--list` view and the session-start nudge (both assignee-scoped via `queue-view.sh`) — an author-scoped drain would show a teammate a ticket in their nudge yet skip it here (the displayed-vs-drained mismatch):

```bash
ME=$(gh api user --jq .login)
# --limit is a HARD cap (gh defaults to 30) — set it above the queue size.
# Pass --label twice for AND semantics: the QUEUE label + an optional TYPE label
# (for example `bug`) to scope a run to one work-type. createdAt is
# pulled for the oldest-first strategy below.
gh issue list --repo "$REPO" --label "<queue-label>" [--label "<type-label>"] \
  --state open --limit 200 --assignee "$ME" \
  --json number,title,labels,createdAt,projectItems
```

**Scope the queue (label + type + who).** Default queue label **`$QUEUE_LABEL`** (the `queue_label` setting — the dedicated handoff label `/queue:bug-hunt` and manual triage both stamp by default), default scope **`--assignee @me`**, no type filter. A `--label`/`--type`/`--assignee` on the command line takes precedence and is used as-is; **`--author <login>`** is available as an alternate scope (creator-, not owner-, scoped) for the rarer "issues I filed" case. **Surface `$QUEUE_LABEL`-labelled tasks alongside any other label** so the operator sees the dedicated queue even when they named a different label. In a non-interactive resume, reuse the recorded choices. If a type filter yields zero issues, warn and confirm before proceeding (a queue label + an unrelated primary label can legitimately be empty).

**Show the queue before asking a selection question — interactive runs only.** Render the fetched issues as a scannable table (number, primary type label, title, age), *then* ask — offer any scope change (`yours` = assigned to you / `all assignees` / a specific `<login>`) and an optional ticket-type filter (a type label) — so the operator confirms-or-narrows against what is on screen rather than picking blind. **Never fire a scope / type / strategy `AskUserQuestion` before this table is shown.** Skip the table only when no selection question remains to ask: a `--resume`, trailing issue numbers, or a command line that already pinned label + scope + strategy.

**Pick the processing order (strategy).** With the table shown, ask the operator to **either name the specific issues to run or choose an order** — naming numbers off the on-screen table is a primary path (the `pick-list` row below), not a fallback. Skip if `--strategy` or trailing issue numbers were given, or recorded on resume. Default with no strategy: **explicitly** `sort_by(.number)` then **highest priority first** (`gh issue list` returns newest-first, so the order must be applied, not assumed). Every strategy below sorts the fetched JSON itself — never rely on gh's default ordering.

| Strategy | Order | How it's read |
|---|---|---|
| `priority` | the board's Priority order (e.g. P0→P1→P2), unset last | Priority is **not** in `gh issue list` JSON — batch-read it per issue via GraphQL `fieldValueByName(name:"Priority")` |
| `label-class` | group by the primary type label, operator-named order | from `labels` in the list JSON |
| `oldest` | `sort_by(.createdAt)` ascending | `createdAt` in the list JSON |
| `smallest-estimate` | Estimate ascending, unset last | Estimate is **not** in the list JSON — GraphQL `fieldValueByName(name:"Estimate")` per issue |
| `pick-list` | exactly the issue numbers the operator named, in that order | the trailing `issue numbers...` arg |

`priority` and `smallest-estimate` need a one-time GraphQL field-read across the queue before sorting, and a board (`github_project`) — see `/ship:github-issues` for the project fields and the `fieldValueByName` read pattern (single source; do not re-derive them here).

### Integration-branch drain (`--integration-branch <name>`) — dependency-aware

**Absent ⇒ the flat behaviour** (each slice branches off `origin/$BASE` and ships its own PR to the base branch; no dep-parsing). Present ⇒ drain the whole breakdown in dependency order onto one long-lived integration branch, with a single human-reviewed integration→base-branch PR at the end. The model, the `git merge`-not-`gh pr merge` mechanism, and the human touchpoints live in [run-ledger.md](run-ledger.md) "integration-branch drain"; Step 1 only computes **readiness**:

1. **Ensure the integration branch exists**, cut from the current base branch — ask the **remote**, not a stale tracking ref (a fresh checkout has none): `git fetch origin "$BASE"; git ls-remote --exit-code --heads origin <name> >/dev/null 2>&1 || git push origin "origin/$BASE:refs/heads/<name>"`. If it already exists, **never** re-push the base branch onto it (that would reset in-flight integration work) — just `git fetch origin <name>`. (Pushing a branch other than the base branch is permitted; see [run-ledger.md](run-ledger.md).)
   - **Give the integration branch its own long-lived worktree — never let it land on the main checkout's HEAD** (the Step-4 sync, the Step-3.6 per-slice merges, and the Done PR all run *on* the integration branch, so with no dedicated worktree they default to the main checkout and strand it off the base branch). Resolve the main checkout once and reuse-or-create the worktree **explicitly** — do **not** `2>/dev/null` the `git worktree add`, or a "branch already checked out" failure falls through to a missing `$INT` that Step 3.6/4 then run against:
     ```bash
     MAIN="$(dirname "$(git rev-parse --path-format=absolute --git-common-dir)")"
     INT="$MAIN/.claude/worktrees/ship-queue-integration-<name>"
     # Ask git's worktree registry, NOT `rev-parse --git-dir`: $INT sits *inside*
     # the main worktree, so for a stale plain dir rev-parse walks up to the main
     # .git and "succeeds", and the checkout below would then switch the MAIN
     # checkout to <name> — the very stranding this step prevents.
     if git worktree list --porcelain | grep -Fqx "worktree $INT"; then
       git -C "$INT" checkout <name>     # registered worktree — reuse it
     else
       git worktree add "$INT" <name>    # create; let errors surface (a stale non-worktree dir → loud "already exists", never a silent checkout into main)
     fi
     ```
     Then hydrate `$INT` with the worktrees plugin, if installed (its `worktree-hydrate.sh "$INT"`), so it can boot a local backend for an integration e2e.
     Then **assert before any later step uses it**: `git -C "$MAIN" branch --show-current` is `$BASE`, and `$INT` exists and is on `<name>`. Every integration-branch git op (Step 3.6, Step 4, Done) runs `git -C "$INT" …`.
2. **Parse `Depends-on` per candidate.** The precheck already does `gh issue view <n> --json …`; also fetch the **body** and parse `## Execution` → `**Depends-on:**` for every `#\d+`. Empty / `—` / `none` ⇒ no deps. Handle multiple.
3. **A dep `#M` is *satisfied* iff its slice is *merged into the integration branch*** — NOT keyed on the base branch (slices never touch it until the final PR). Derive it from git+GitHub, not the ledger string: (a) if `#M` has a ledger row, `done` **and** its recorded merge-commit SHA reachable from integration; (b) **if `#M` has *no* ledger row** — it merged in a *prior* run, or pre-exists this drain (e.g. a dependency already shipped before the queue was built) — it is satisfied iff its **issue is closed AND a commit referencing it is reachable from the integration branch** (`git log origin/<integration> --grep "#M"` finds the merge, or the issue's close comment records the merge SHA). Never silently treat a closed-but-not-reachable dep as satisfied. (b) is what lets a dependent be `ready` immediately against a dep that is not in this run's ledger; on resume, (a) is also re-derived from reachability, never trusted from the ledger alone (Step 6.5 self-verification).
4. **Readiness is a filter applied *before* strategy ordering.** Of the issues whose deps are all satisfied (`ready`), the chosen `--strategy` still orders them. A dep-not-satisfied issue is parked `waiting` — a **new ledger status distinct from `blocked`**: no marker comment, no `Status=Blocked`, no grounding subagent spent, board Status untouched. It auto-promotes the moment its deps land (Step 4). `waiting` is never the `pick-blocker` path (that stays for a real human-sign-off dependency — [blocker-protocol.md](blocker-protocol.md)).
5. **Surface unresolved deps distinctly.** If `#M` does not exist, is closed-unplanned, or is outside the queue scope ⇒ a warning row `waiting-on #M (unresolved: …)` — neither silently satisfied nor waited-on forever.

**RFC-table-as-queue + just-in-time issues (`--from-rfc <path>`).** A breakdown does not need its issues filed up front — everything a slice needs already lives in the RFC. With `--from-rfc <path>` the **RFC's `## Task Breakdown` table is the queue**: each row is a slice, read directly. **`--from-rfc` requires `--integration-branch`** — its whole readiness model is *dep merged onto the integration branch*, so without that branch there is nowhere to evaluate deps or unblock waves; **fail fast if `--from-rfc` is given without `--integration-branch`** (do not fall back to flat base-branch-target behaviour for a multi-slice RFC). Readiness and the wave DAG are computed from the table's `Depends-on` column **read as *slice IDs*** (the `#`-column identifiers) — note this **differs from the pre-filed-queue mode above, which reads `Depends-on` as `#N` issue numbers**; the *satisfied = dep merged onto integration* rule is the same, only the identifier space differs. Each slice's GitHub issue is created **just-in-time the moment the slice enters the `ready` set** — the **initial deps-free wave at Step 1**, and each later wave at its **Step-4 promotion** (its dep issues exist by then). Creation is from the row via the task-brief template, translating slice-ID deps to the dep issues' `#N`. **The very first deps-free slice is created at Step-1 build, not deferred to a promotion it never gets** — else an RFC whose wave 1 is dependency-free would stall before it starts. The per-issue precheck (open-PR / resume / blocked-marker, below) applies to a from-rfc slice **only after that JIT issue exists**; an un-created later-wave slice is pure `waiting`, tracked by **slice ID** (it has no issue to check yet). **`--integration-branch` *without* `--from-rfc` still consumes a pre-filed queue** (both supported). The skill's own fail-fast precondition is a **clean slice-ID DAG** (every `Depends-on` a real row, no cycle — else stop, naming the offending row). One more check is **cheap and only observable here**: read the table's framing block for the `Ground-verified:` provenance stamp. **Absent ⇒ narrate it and drain anyway** — "draining an unstamped (first-cut) table: its `Depends-on` edges were derived from the design, not checked against the code" — because many RFCs carry no stamp, so pausing on absence would halt most drains in a skill built to run unattended. **Present but broken** — the SHA does not resolve, or the edge count disagrees with the table — is different: that is a false provenance claim, so **stop and ask**, as a queue-wide pause (Step 5). The doc reviewer cannot make either call (it sees a path, not an imminent drain), and this is the last point where they can be made in time. That the table was otherwise *reviewed* remains the operator's upstream handoff, same as the queue-label handoff. The JIT mechanics (slice-ID → `#N` translation, the ledger's slice-ID column, what resume re-reads) live in [run-ledger.md](run-ledger.md) "`--from-rfc`".

**Step-1 table gains a readiness column + a wave view + an integration header.** Before any work starts, render:
```
integration/<rfc> · 3 ahead of <base> · synced 12m ago

| issue | type | title | age | readiness |
|-------|------|-------|-----|-----------|
| #a | … | … | … | ready |
| #c | … | … | … | waiting on #a |
| #z | … | … | … | waiting on #131 (unresolved: no such issue) |

Wave 1 (ready): #a #b · Wave 2 (waiting on wave 1): #c #d
```
so the operator sees the dependency shape and what releases each parked wave before the drain begins.

**Dropping the per-slice merge gate drops more than its result.** An operator may reasonably skip the per-slice merge gate when the slice PRs target a private integration branch, since a gate scoped to the base branch does not apply there. But a merge gate usually runs more than the build and tests: architecture tests, linters, the formatter, generated-code drift checks. Several of those enforce classes a review panel is bad at and a build is blind to. So when the per-slice gate is dropped, run its local equivalents per slice rather than treating "it builds and the tests pass" as the same bar. The formatter check is often a separate invocation from the linters, so include it explicitly.

**`--limit N` caps issues PROCESSED this run** — the overnight safety valve while the usage-pacing layer is experimental: ship at most N, then stop and report the remainder for the next run. (Distinct from the `gh issue list --limit 200` *fetch* cap above.) With no `--limit`, the run drains the whole queue and leans on the experimental usage-pacing, which is not hardened — so for an unattended overnight run, **always pass `--limit N`.**

**Per-issue precheck before grounding** (the list does not carry enough to skip on): read each candidate's live state with `gh issue view <n> --repo "$REPO" --json state,stateReason,projectItems,comments` (Status, marker comments) and **skip** it if already `In Review`/`Done`. For the **open-linked-PR** check, do **not** rely on `gh issue view --json closedByPullRequestsReferences` — that projection misses a **draft** PR (and a just-opened one before GitHub indexes the link), which would let the loop open a *second* PR for an issue it already shipped. Use the robust GraphQL linkage (timeline `CONNECTED_EVENT` **+** `closedByPullRequestsReferences(includeClosedPrs:true)`); skip the issue if that returns any OPEN PR. If the issue carries an unresolved `<!-- ship-queue:blocked v1 -->` marker, apply the [blocker-protocol.md](blocker-protocol.md) resume rule (skip again unless a human reply/body-edit postdates and resolves it). **Resume, do not restart:** an issue already `In Progress` with an existing `.claude/triage/brief-<issue>.md` or worktree was interrupted — resume it rather than re-grounding and opening a second worktree/PR. **In `--integration-branch` mode**, also park a `waiting` issue (readiness filter above) *before* grounding — a not-yet-ready slice spends no grounding subagent and gets no marker; it is re-evaluated for promotion at each checkpoint (Step 4). **In `--continue` mode the open-PR skip is inverted:** an issue with an open PR is NOT skipped — it enters the assess→advance path ([continue-mode.md](continue-mode.md)) instead of grounding a fresh fix.

## Step 2 — Per issue: GROUND (subagent)

Mark the issue `In Progress` (`/ship:github-issues` field flow). Launch a grounding subagent to produce a tight **implementation brief** — and nothing else (no edits). The brief is a **fixed four-field template, capped at ~60 lines** (it is read into the main loop every issue, so length is per-issue context tax):

- **root cause** — confirmed against the **current** code (the issue body may be stale — re-verify `file:line`). **For a bug / evidence-backed issue**, it must be a mechanism that actually **fires on the issue's cited evidence**: a code path that merely *could* produce the symptom, or that does not match the cited status / vendor / site, is not a confirmed root cause (reachability is part of the confirmation, not a later step). **A feature / refactor / RFC slice carries no prod evidence — there is no evidence-match to make; ground it against its RFC anchor + acceptance criteria (the RFC-slice grounding below), and this field states the design mechanism, not a root cause;**
- **exact edits** — the files + lines and the precise change; the contrasting correct-sibling to mirror, if the issue named one;
- **test** — the test to add (reproduce-first for a defect) and how to run it;
- **blockers** — anything that should *block* an autonomous fix (ambiguous root cause, schema/migration, cross-service contract, security/authz semantics needing human sign-off, or a scope larger than the issue asks). **Read the declared gate first, before deriving anything:** a task-brief issue carries `Execution.HITL / AFK` and a `--from-rfc` slice carries the table's `HITL/AFK` column. A slice whose tag resolves to **gated is a blocker by declaration** (`human-gated`, blocker-protocol.md — which points at the contract's leading-token resolution rule, states why an unresolvable cell fails **closed** to gated, and defines when an already-discharged marker exempts a slice from re-blocking on a resume). The tag names a decision the breakdown author deliberately reserved, so honour it rather than re-deriving whether it matters; the brief carries that slice's stated decision as the `Needed from you`. Deriving the other blockers is unchanged — the tag adds a declared gate, it does not replace the judgment. **An efficacy gap is a blocker too:** for a **bug / evidence-backed** fix, if its active path does not fire in prod (dead / rare code), does not move the issue's cited evidence, or is single-site for a symptom the evidence shows is vendor/site-agnostic; and for **any** change (bug or feature), if it is claimed "strictly better / never worse" yet regresses some axis under a worse-case (interrogate the claim, do not take it at face value) — flag it. A change that looks right but does not do the job is a mark-and-continue blocker, not a silent ship.

These four fields are the *whole* brief — no restating the issue, no pasted code dumps, no narration of the search. A brief over the cap is padding: **trim to fit without dropping a field** (a missing field is a failed brief, not a shorter one). Write the brief to the **main checkout's** `.claude/triage/brief-<issue>.md` (gitignored — pin the dir to the main checkout via `git rev-parse --git-common-dir`, the same trick the ledger uses, run-ledger.md, so the per-issue worktree Step 3 cuts can resolve the brief by absolute path and copy it in). Only the structured brief returns to the main context. **If it flags a blocker, do not ship — go to Step 5 (mark and continue), do not stop the queue.**

**Adjacent findings — a mandatory, *separate* return (not a fifth brief field).** If the grounding subagent spots an **initiative-relevant defect outside this slice's scope** that it must not fix in-slice (a pre-existing bug in a sibling, a systemic gap the slice only brushes), it does **not** bury it in prose or drop it: it appends a structured row to `.claude/triage/adjacent-<issue>.json` and notes `adjacent: N` in its return. The main loop auto-files each as a follow-up issue under the parent at the next checkpoint (Step 4). Empty is the norm; the channel exists so a real out-of-scope finding is escalated, never silently lost. Schema + auto-file + idempotency: [run-ledger.md](run-ledger.md) "adjacent findings".

**Route the grounding by the issue's `Execution.Implementing skill` field (route the grounding, not the build).** Parse the issue body's `## Execution` → `**Implementing skill:**`:
- **`/skill-name`** → the grounding subagent **reads that skill** before tracing the code, so the brief carries the right surface's conventions (token system / contract / package placement). Skills and agents here are the repo's own, discovered at run time. For a frontend slice, run grounding **as the repo's own frontend agent**, if it has one (it already *is* the FE-surface authority), instead of `general-purpose`.
- **Two skills, comma-separated** (`/api-skill, /frontend-skill`) → the Task Breakdown allows a genuinely-atomic slice to name **both** build skills; **read every named skill** so the brief carries *all* the surfaces' conventions (and use the frontend agent, if any, for the FE one). Do not silently route to just the first.
- **`none — <reason>`** → ground from **RFC + code only** (a pure refactor / one-off script / no owning surface) — no skill to read.
- **`/skill-name (verify — may be stale)`** → read the skill for orientation but **do not treat it as gospel** — verify each convention against the live code, and note in the brief where the skill and the code disagree. Never silently trust a flagged-stale skill. (The `(verify — may be stale)` flag attaches per-skill in a two-skill row.)
- **Field absent / unparseable** → default to a `general-purpose` grounding subagent on RFC + code; do not guess a skill.

The skill shapes **how** the four fixed fields are derived — it does **not** add a fifth field. Surface conventions (token system / contract / package placement) land **inside `exact edits`** (the right pattern to mirror, the correct placement) and sharpen `root cause`; the brief stays the capped four-field template. This routes the **grounding subagent only** — the fix is still applied in the **main loop** (Step 3), so the commit gate / self-check / the review cadence still fire. Spawning an agent to do the *edits* would skip those hooks; never do that.

**RFC-slice grounding is thorough and evidence-bound (integration-branch / `--from-rfc`).** When the task is an RFC slice — it carries an `RFC anchor` (the `--from-rfc` table column) **or**, for a **pre-filed task-brief issue**, a `References.RFC` / `Grounding` pointer (where the task-brief maps that same column, so a hand-filed RFC slice in plain `--integration-branch` mode is **not** mistaken for an ordinary issue and skipped) — the issue body is a *summary* of the design, not the design, so the grounding subagent must read, before tracing code: **(a)** the **anchor section(s) in full** (not the issue's paraphrase); **(b)** the sections the anchor **cross-references** and the **Decisions Log rows** the slice rests on — the invariants and trade-offs it must honour, including ones that span sections (e.g. a fail-open-here / fail-loud-there rule); **(c)** the **merged code of the deps** on the integration branch (the *real* contract a dependent builds on, never the assumed one). The brief must **cite** what it grounded in — the anchor §, the specific Decision #s, the cross-section invariant — *inside* `root cause` / `exact edits` (still no fifth field). The citation is the point: a brief that grounds only in the issue body + code, with **no RFC citation for a slice that has an anchor, is incomplete — re-ground.** The missing citation is the detectable signal, so "I read the RFC" cannot be self-asserted.

> **Source of truth = the GitHub issue.** ship-queue's only required input is the issue itself (queue from `gh issue list`, content from `gh issue view`). It needs **no** pre-existing local artefacts — a teammate on a fresh machine can run it with an empty `.claude/triage/`. The brief is a *derived, regenerable* resume cache, not an input: if it is genuinely missing, just re-ground from the issue. (Step 3 reads the brief by absolute main-checkout path, so "the worktree can't see it" is **not** a reason to re-ground a brief that is on disk — re-ground only when `test -f "$MAIN/.claude/triage/brief-<issue>.md"` fails.) So every bug's grounding must live in the issue body; an upstream batch file is never read here. **(`--from-rfc` exception:** the RFC's Task Breakdown is additionally read — to *create* the issue JIT (Step 1) and to ground the slice (above). The RFC is durable in-repo on the integration base, addressable by path, **not** a transient batch artefact — so the no-throwaway-input spirit holds; and once the issue exists it remains the shipping source of truth.)

## Step 3 — Per issue: SHIP (main-loop write path, subagent cognition)

Run the **write path** in the main loop so the harness fires. The **inline steps below are canonical** for ship-queue — they carry the token-isolation invariants (the merge gate as a zero-token background-Bash run, bounded panel returns) that a long unattended drain needs. You *may* reuse `/queue:ship-task <issue>` as the spine for the worktree → fix → prove → `/ship:pr` + merge gate ordering, feeding it the Step-2 brief — `/queue:ship-task` runs the merge gate inline in its own main loop, and a command gate runs as background Bash either way (step 6), so the gate's token cost is fine either way. For a short attended drain, reusing the spine is an accepted trade-off; for an unattended overnight drain, prefer the inline path so the ledger + bounded-return invariants stay explicit. The steps:

1. **Per-issue worktree** (isolation → one branch, one PR), named **`ship-queue-<issue>`** (dir `.claude/worktrees/ship-queue-<issue>/`) — never a random name, so a post-compaction resume locates the interrupted worktree deterministically from the issue number alone (run-ledger.md "reconstruct"). One issue in flight at a time. **Always create the slice branch `ship-queue-<issue>` with `-b`** — `git worktree add -b ship-queue-<issue> <dir> <base>` — never `git worktree add <dir> <base>` (that checks out `<base>` itself, so edits land on the shared base and `gh pr create --base` has no distinct slice head + Step 3.6 finds no `ship-queue-<issue>` to merge). **Base:** flat mode = fresh `origin/$BASE` (verify freshness by the remote, not by commit-log inference — see `/queue:ship-task`'s reference, "Verify the base is fresh by the remote"); **`--integration-branch` mode = the integration branch** (`git fetch origin <name>; git worktree add -b ship-queue-<issue> <dir> <name>`) so the slice branches *off* integration and already has its merged-dep code.
   - **Hydrate the fresh worktree immediately** (the worktrees plugin, if installed) — raw `git worktree add` honours no `.worktreeinclude` and never fires the `EnterWorktree` hook, so without this the slice worktree is missing the main checkout's local, untracked config and secrets, and a local backend run can fail. Right after the `git worktree add`, run the worktrees plugin's `worktree-hydrate.sh <dir>` — idempotent and non-fatal (always exits 0), it copies the listed local files from the main checkout. Resolve `$MAIN` once as the parent of the shared git dir: `MAIN="$(dirname "$(git rev-parse --path-format=absolute --git-common-dir)")"`.
   - **Heavy deps are not hydrated either.** Hydration copies local config only, never `node_modules` / `.venv` (they break when copied). If the slice touches code whose build, code generation or tests need installed dependencies, install them in the slice worktree (for example `pnpm install`, `uv sync`) before a build or the merge gate run. A slice that needs none skips this.
   - **Carry the brief into the worktree.** The Step-2 brief lives in the main checkout's gitignored `.claude/triage/`, which does not cross the worktree boundary. The **canonical** reach is the absolute path `$MAIN/.claude/triage/brief-<issue>.md` — never worktree-relative (the absolute path also survives a worktree Read/Edit pinning to the main checkout); as a convenience for relative readers also `mkdir -p "<dir>/.claude/triage" && cp "$MAIN/.claude/triage/brief-<issue>.md" "<dir>/.claude/triage/"` (the `mkdir -p` is required — `.claude/triage/` is gitignored, so a fresh worktree has no such dir and a bare `cp` fails with `No such file or directory`). Presence is **checkable, not asserted**: `test -f "$MAIN/.claude/triage/brief-<issue>.md"` — a present file is authoritative (read it), and only a failing `test -f` is truly-absent → re-ground.
2. **Apply the fix** per the brief, in the main loop (Edit/Write → the commit gate + self-check fire). Add the test first when reproducing a defect.
3. **Commit** in the main loop (→ review-cadence counts it). Keep the change surgical.
4. **When the review-cadence nudge fires, run the panel with full-lens rigor** — lens routing read at run time, not improvised (next subsection) — and clear Critical/Important before proceeding — soft, never blocks, but do not skip the run.
5. **Open the PR ready — not a draft** — in the main loop with `Closes #<issue>` — a merge gate that runs against a PR needs the PR open first, so the PR must exist before the gate. A ready PR is an open PR for the gate just as well, and opening ready (never `--draft`) lets the hosted Codex review start immediately; a draft blocks that review and hides the issue↔PR link a downstream check relies on. Because Codex reviews from the first commit, a Step-6 merge-gate fix commit leaves that review **stale** — re-run the codex-sweep after any gate-fix push so its verdict covers the **final** head, and never let a pre-fix `done-clean` satisfy the done-gate (settle codex on the reviewed head, not an earlier one). **Base:** flat mode targets `$BASE`; **`--integration-branch` mode targets the integration branch** (`gh pr create --base <name>`). Note `Closes #<issue>` does **not** fire on a non-default base — Step 3.6 closes the issue explicitly on the integration merge.
6. **The merge gate — the zero-token run as a background Bash, not an LLM subagent** (token isolation: never run the build/test/lint in the main loop as raw commands). When `GATE` is a command, launch it as a **background Bash** task and end your turn — the multi-minute wait costs **zero** model tokens. When `GATE` is a label, apply it to the PR; when `GATE` is blank, the base branch's required checks are the gate. For a label or blank gate, wait on `gh pr checks <PR> --watch` as a background Bash. On completion, read only the compact verdict (the gate's own summary line, or the checks' pass/fail). Do **not** read the full run log into the main loop. Queue-specific consequences: **still running** keeps the row in progress and waits/polls the owning run instead of launching another; **pass** contributes the gate prerequisite to the done-gate; no other state may mark the row done. A **fail** is the one case that needs cognition (main loop or a `fix-scout` subagent, Step 3 "Fix ownership") before a plain rerun. Do not spend a whole LLM subagent turn relaying a deterministic verdict.
7. **`/ship:pr` finalize** — reconcile per `/ship:pr-communication`; Validation = the actual merge gate + panel result, past tense. (The PR was opened ready at step 5, so there is no draft to flip.) **Fold any post-open fixes as new commits, never `git commit --amend`** — amend forces a force-push (a permission prompt), and a squash-merged repo collapses the commits anyway (only amend a never-pushed commit). **Announce** the PR through `/ship:pr`'s announce step (the `announce_channel` setting; blank skips it) — in flat mode every per-slice PR announces; in `--integration-branch` mode **only the final integration→base-branch PR** announces (per-slice integration PRs stay suppressed — see the integration-drain announce below). Whichever announces uses `/ship:pr`'s **exact one-line format**, never a free-drafted multi-line post; operator-facing notes (a scope decision, a follow-up, a deploy order) belong in the **PR body**, not the channel — the announce shape is invariant to how interesting the PR is. Pass `--no-announce` through to `/ship:pr` for a PR that must **not** post to the channel: **a per-slice `--integration-branch` PR** (suppressed per the carve-out above — only the integration→base-branch PR announces). For a real, **base-branch-targeting** PR (flat mode, or the integration→base-branch PR), never thread it — that PR must announce.

Record the row in the ledger as you go (`run-ledger.md`). It flips to `done` only when panel Critical/Important cleared **and** the merge gate green **and** codex settled.

**If the slice produces a prod-facing artifact** — a rollout runbook or flag-flip doc — its prod identifiers (account, tenant or resource ids) must be resolved from the **authoritative prod source**, **never** the local/dev id observed during this slice's e2e. Local e2e rightly uses locally-created data; carrying that local id into the prod runbook's commands would point an operator at something that does not exist in prod.

### Full-lens panel rigor + bounded returns

The panel is the per-issue quality gate, and an under-scoped panel misses real Critical/Important findings. Run it **properly**, not as a hand-picked mini-panel:

- **Lens routing is not yours to choose — read it at run time.** Open the `/review:review-panel` skill's **Step 2** (the single routing authority) and apply its table to *this diff's* file-set to get the fitting lens set; do not subset it, do not improvise from memory. By construction this makes the routing's always-on lenses mandatory (for example its team-rules lens on every non-docs diff when the team has rules, and **`matcher`** on any regex / matcher / glob / selector / classifier / boundary-check change) — the lenses a hand-picked subset tends to drop. A panel that omits a fitting lens is a process violation, not a judgment call.
- **One fresh subagent per lens** — never bundle multiple lenses into one agent. Each gets the lens's **verbatim Focus**, no paraphrase.
- **Worktree-safe diff delivery** — write the diff to a temp file and pass the **correct worktree path**. A reviewer agent with no Bash, given no path, reads main-repo files and emits false findings (Read/Edit from a worktree session can resolve to the main checkout).
- **Bounded returns (token isolation):** each lens subagent **writes findings to `.claude/triage/panel-<issue>/<lens>-<round>.json`** (`/review:review-panel` Step 3 owns the naming — the round suffix keeps an earlier round available for its regression diff) and returns a **one-line count** (`<lens>: C<n>/I<n>/M<n>`). The main loop reads only the consolidated Critical/Important set (see [run-ledger.md](run-ledger.md)). (Keyed on the **issue**, not the PR — the panel fires on the cadence nudge *before* the PR is opened.)
- **Emit a per-PR lens manifest + the reviewed HEAD SHA** into the ledger row — `lenses=[…] skipped=[…] @ <reviewed-sha>` (the fitting set that ran + any skip + the commit the panel last covered): the after-the-fact audit that the full set ran, so a thin/missed panel is detectable. A row cannot flip `done` while the manifest shows a fitting lens silently dropped. Schema, the `skipped=` whitelist-reason rule, the reviewed-SHA cell (why it makes a stale panel detectable while `/review:review-panel` stays non-posting, and how `/ship:pr` mirrors it into Validation), and the done-gate: [run-ledger.md](run-ledger.md).
- **Step 2.6 cross-model lenses run on *every* slice — always-attempt, not a fallback.** `/review:review-panel` Step 2.6 is "pre-pr run — always attempt", and its engine set is a **registry read at run time** (the same "routing is not yours to choose — read it at run time" rule as Step 2 above; **do not hardcode a model here**). Run the automatic counterpart and OCR the way the `/review:review-panel` skill's Step 2.6 specifies — as separate background Bash calls, each with `--base "$(git merge-base <base> HEAD)"`. The counterpart is Claude for a Codex author and Codex for every non-Codex author. Do **not** gate this on the hosted codex-sweep: the local counterpart review and hosted Codex sweep are independent surfaces at different times. Each engine records `SKIPPED`/`FAILED` as **absent, not clean** and never blocks or loops. Fold `FINDINGS` in like any panel finding; record each outcome in the **panel manifest**, never the ledger `codex` cell, which remains reserved for the hosted sweep's stop-state.
- **Converged-finding rule:** if ≥2 independent lenses flag the same thing, do **not** self-clear it — verify against source or build a repro first.
- **Adjacent findings escalate, they are not dropped.** A lens that flags an **out-of-diff, initiative-relevant** defect (not a generic nit) emits it to the adjacent-findings backlog (`.claude/triage/adjacent-<issue>.json`) instead of dropping it or burying it in prose — the main loop auto-files it as a follow-up under the parent ([run-ledger.md](run-ledger.md) "adjacent findings"). In-diff Critical/Important still go to the per-lens JSON and are fixed in-slice (above); the backlog is **only** for what is correctly outside this slice's scope.

### Fix ownership of panel findings

- **Surgical / mechanical Critical+Important → the main loop applies directly** (the edit is cheap, and re-firing the commit gate/self-check + a panel re-review of the delta is exactly what we want).
- **Exploratory fix → a `fix-scout` subagent returns a surgical fix-plan** (file:line + the exact change + the test); the **main loop applies it**.
- **Never let one subagent both explore AND commit the fix** — explore in a subagent (plan only), apply in the main loop.

## Step 3.5 — Codex sweep this PR (before moving on)

`/ship:pr` launches the background `await` waiter for `/ship:codex-sweep <PR>` (unchanged by token isolation — the panel and the sweep still run; only their returns are bounded). The wait is a zero-token shell poll loop, not an LLM turn per poll.

> **The loop stays synchronous per PR.** Do not start the next issue until this PR's `codex` ledger cell records a stop-state — Step 3.6's merge step reads that cell. Each PR's sweep waits in its own background `await` process (zero tokens), so per-PR waits never contend. The queue serializes **by construction** (one issue at a time, each PR's sweep settled before the next begins) because the ledger gate needs it. There is no batch/all-PRs-at-once sweep.

Drive **that PR's** sweep to a stop state (`done-replied` / `done-reviewed` / `done-clean` / `codex-limited`, or `no-show` if the bounded wait is exhausted) before the next issue:

- Run `/ship:codex-sweep <PR>`; fix the clear-cut findings, reply on each thread (leave open).
- If the sweep committed fixes, **re-run the merge gate as a background Bash** — the sweep's commits advance HEAD, which is the case a plain run already covers (same zero-token path as Step 6, not an LLM subagent).
- **If the signal is `analyzing` or `absent`** (Codex still working, or not yet picked up — *not* stop states), **do not launch another awaiter.** `/ship:pr` already launched the per-PR background await (the `/ship:codex-sweep` skill's documented await command) when it opened this PR (the arming step above), so **wait for that task to complete** — it re-invokes you once, when Codex settles or the bounded wait is exhausted. Launching a second `await` for the same PR would race the first: two completion wakeups acting on the same finding (duplicate fixes/replies) or at least duplicate LLM turns, breaking the single-settle gate. Only launch one yourself, with the `/ship:codex-sweep` skill's documented await command, if none is outstanding (e.g. `/ship:pr` skipped arming, or a manual `/ship:codex-sweep` outside the queue). That `await` is a zero-token shell poll loop bounded by its own analyzing/absent limits; `/ship:codex-sweep` flips `analyzing`/`absent` to the `codex-limited` stop-state once Codex posts a usage-cap notice **in a top-level comment *or* a review body**, so a capped sweep — auto or manual `@codex review` — can't wedge the wait. The wait stays on this one PR; it is never carried into the next issue. **If `await` reports `wait-exhausted`** — its bounded wait elapsed with no review (Codex never picked the PR up, no usage-cap notice) — record `codex=no-show` in the ledger and treat it as a terminal stop-state so the loop advances. Without this terminal the gate below would wedge the queue forever on a PR Codex simply never reviews; the PR still shipped behind the merge gate + the panel, so `no-show` is a degraded-but-safe settle, not a quality bypass.
- **The codex cell must hold a *genuine* terminal — `skipped (usage-capped)` is not one, and never `⚙`-merges (Step 3.6).** A usage cap is not a licence to merge un-swept and defer to a later backlog pass: `/ship:codex-sweep` detects the review-body cap, so a capped sweep resolves to **`codex-limited`**, and an exhausted wait resolves to **`no-show`** — both real stop-states. Writing a manual `skipped (usage-capped)` into the codex cell and advancing does **not** satisfy the gate; drive the sweep to one of `done-replied` / `done-reviewed` / `done-clean` / `codex-limited` / `no-show` first.
- **On `codex-limited`/`no-show`, ensure the local cross-model lenses ran — re-attempt if the pre-pr run came up absent.** Re-run the `/review:review-panel` skill's Step 2.6 counterpart and OCR engines as separate background calls, with `--base "$(git merge-base "origin/$BASE" HEAD)"`. On `<ENGINE>-LENS: FINDINGS`, fold findings in normally; any `SKIPPED` or `FAILED` outcome means that review was absent, not clean. Never loop on absence and never let a soft engine outage block shipping behind the merge gate plus the same-runtime panel, but fix Critical/Important findings before marking the panel settled.
- Then exit the worktree keeping it (ship by branch name; never check the feature branch into the main worktree).

## Step 3.6 — Merge onto integration (`--integration-branch` mode only)

In flat mode this step does not run — the slice PR stays open against the base branch for a human to review+merge, and the loop moves on. In integration mode, once the slice's full gate is green (the merge gate green **+** panel C/I cleared **+** codex at a **genuine stop-state** — `done-replied`/`done-reviewed`/`done-clean`/`codex-limited`/`no-show`, *never* a manual `skipped (usage-capped)`, Step 3.5 — the row would flip `done`), **the loop itself merges the slice onto the integration branch** so the next wave unblocks without a human. With permission rules that deny `gh pr merge` but allow `git merge` and a push to a branch other than the base branch (see [run-ledger.md](run-ledger.md)), run the merge **in the integration worktree from Step 1** (`INT=.claude/worktrees/ship-queue-integration-<name>`) — never check the integration branch out in the main checkout:

```bash
INT=.claude/worktrees/ship-queue-integration-<name>   # the dedicated worktree from Step 1
git -C "$INT" fetch origin <integration>
git -C "$INT" checkout <integration> && git -C "$INT" pull --ff-only
git -C "$INT" merge --no-ff ship-queue-<issue> -m "ship-queue: merge #<issue> onto <integration>"
MERGE_SHA=$(git -C "$INT" rev-parse HEAD)   # record in the ledger row — the satisfied-dep proof
git -C "$INT" push origin <integration>     # a push to a non-base branch is permitted
```

**First post the durable PR↔issue cross-reference, then close.** `git merge` posts nothing, and `Closes #N` is inert on a non-default base — so a draft/integration-base PR is invisible to GitHub's linkage projections and the issue timeline has no clickable PR link. Before closing, run `gh issue comment <issue> --repo "$REPO" --body "Shipped via PR #<pr> (merged to <integration> @ <MERGE_SHA>)"` — the `#<pr>` mention creates a visible **bidirectional** cross-reference (a timeline event on both the issue and the PR), durable independent of whether the close below succeeds.

Then **explicitly close** what `git merge` does not (`Closes #N` only fires on a default-branch-base PR): `gh pr close <pr> --repo "$REPO" --comment "merged to <integration> via ship-queue (<MERGE_SHA>); will reach <base> via the integration→base-branch PR"`, `gh issue close <issue> --repo "$REPO" --comment "shipped to <integration> via ship-queue (<MERGE_SHA>)"`, set Status appropriately, and delete the slice branch (`gh api -X DELETE "repos/$REPO/git/refs/heads/ship-queue-<issue>"` — its commits live in integration now).

> **DANGER — never run a close with an unvalidated number.** `gh pr close` / `gh issue close` with an **empty or missing** number argument falls back to **the current branch's PR/issue** — so an unset `$pr` (e.g. a `gh pr create` that errored and parsed to "") will silently close *whatever PR the current branch has open*, which can be an unrelated real PR. Before the cross-reference comment or any close: **assert the number is non-empty and numeric, and always pass `--repo "$REPO"`** (so it can never resolve against the cwd's branch — and an empty `$pr` never posts a hollow `Shipped via PR #` cross-reference). E.g. `[[ "$pr" =~ ^[0-9]+$ && "$issue" =~ ^[0-9]+$ ]] || { echo "refusing: PR/issue unresolved"; exit 1; }` — guard **both** numbers, since the cross-reference comment embeds `#<pr>` *and* targets `<issue>`. Pin every `gh pr/issue close` to an explicit, validated number — the loop must never let a close target be inferred from the working tree. The slice PR shows **Closed, not Merged** — that is expected (commits are in integration; the feature lands as one squash at the base-branch boundary). **Record `MERGE_SHA` in the ledger row** — it is the durable, git-checkable proof a dependent's dep is satisfied (Step 6.5 re-derives reachability from it). **On any failure of this merge (conflict, push rejected), do not close the PR/issue** — leave the slice shipped-but-unmerged and surface it; a half-merge that closed the issue would strand the chain.

## Step 4 — Usage-paced loop

> **EXPERIMENTAL — dormant by default.** Usage-pacing depends on a statusline capturing `rate_limits` to `.claude/triage/usage.json`, and that statusline is **not wired by default** (a project statusline overrides everyone's personal one). So `should-pause` returns `no-signal` and the loop does **not** pace unless an operator opted into the capture. **Rely on `--limit N`** to bound the run. The steps below are the intended behavior once capture is wired.

If `--limit N` was set, stop after N issues and report the remainder. Otherwise, between issues (a clean checkpoint — never mid-fix), check the real 5h window via the captured signal (`"${CLAUDE_PLUGIN_ROOT}/scripts/statusline-capture.sh"` → `.claude/triage/usage.json`):

```bash
"${CLAUDE_PLUGIN_ROOT}/scripts/usage-guard.sh" should-pause   # -> "pause ..." | "ok ..."
```

- **`ok …`** → continue to the next issue.
- **`pause …`** (real `used_percentage` ≥ 85%) → you are near the 5h limit *while you still have compute*. Do **not** start another issue. `CronCreate(durable:true, recurring:false)` at `resets-at` + ~10min with prompt `/queue:ship-queue --resume --session <session-id> <same args>` — `<session-id>` is the id from this ledger's `# resume-cmd:` header (the original run's), **not** the current (post-resume) session's `$CLAUDE_CODE_SESSION_ID` — then **end the turn**. The REPL stays open; the cron fires after the window resets (fresh budget) and re-enters at Step 6.

Pause *before* the wall (real %): once the hard limit hits there is zero compute to arm anything. The dead-man cron (Step 0) covers a turn that blows past 85% in one go.

If `should-pause` returns `no-signal`/`stale` for several consecutive checks, the statusline capture is broken — pacing is then blind. **Notify the operator** rather than coasting silently on the unverified cron.

**Before grounding the next issue, confirm the just-shipped issue's `codex` ledger cell shows a stop-state** (the Step 3.5 single-armed-sweep invariant). **Then file any adjacent findings at this checkpoint** — read each in-flight `.claude/triage/adjacent-<issue>.json` and auto-file every unfiled row (`filed_issue == —`) as a follow-up issue under the parent via `/ship:github-issues`, idempotent on the `filed_issue` cell, mirroring each into the ledger ([run-ledger.md](run-ledger.md) "adjacent findings"). Loop until the queue is empty (no open in-scope issue without a PR and without an unresolved blocker marker). **In `--from-rfc` mode "empty" is not "no open issue" — un-created later-wave slices have no issue yet, so the completion check (and every resume, below) must *re-read the RFC Task Breakdown* and confirm every slice has shipped (merged onto integration); a queue with no open issues but un-promoted table rows is *not* drained.** Keep the main context lean between issues: briefs and panel findings live on disk in `.claude/triage/`, the ledger is the only state the loop holds, and the harness compacts long context on its own — reconstruct from the ledger when it does (`run-ledger.md`).

### Integration-branch cascade (between waves, `--integration-branch` mode)

The satisfied-gate is "merged into integration" and **ship-queue itself does that merge** (Step 3.6), so no human advances a wave. At each between-issue checkpoint:

1. **Promote.** Re-evaluate every `waiting` row; any whose `Depends-on` are now all satisfied (deps' merge-commit SHAs reachable from integration) **flips `waiting → ready` and ships this same run.** (In `--from-rfc` mode a *promoted* slice's JIT issue is created **here**, on promotion, from its Task-Breakdown row — its dep issues now exist; the *initial* deps-free wave was already created at Step-1 build. Either way, creation is the moment the slice enters `ready`.) Wave 1 merges unblock Wave 2, which unblock Wave 3 — one unattended drain. Narrate it: `merged #a → integration · unblocked #c #d · building #c…`. **`--limit N` counts every slice *shipped* this run — wave-1 *and* auto-promoted — not just wave-1 grounding.** On hitting the limit the drain stops at a clean checkpoint, leaving the rest `ready`/`waiting` for the next run; so the limit bounds total work and a chain never drains unbounded under it.
2. **Sync base → integration *before each wave* (and on every resume).** Over a long drain the base branch moves; if integration drifts, the final PR is one giant conflict. Run it **in the integration worktree** (`INT=.claude/worktrees/ship-queue-integration-<name>`, Step 1), never on the main checkout: `git -C "$INT" fetch origin "$BASE"; git -C "$INT" checkout <integration>; git -C "$INT" merge "origin/$BASE"`. Clean ⇒ `git -C "$INT" push origin <integration>`, continue. **Conflict ⇒ queue-wide pause + notify** (Step 5) — a cross-team conflict is not the agent's to auto-resolve (same class as auth-expiry).
3. **Cycle / stuck detection (must-have).** If a full pass promotes **zero** rows **and** the ready set is empty **and** `waiting` is non-empty ⇒ **stop and report** (name the still-waiting rows + their unmet deps). Never spin re-checking forever. **Name the cause, do not default to "cycle":** rows waiting behind a `human-gated` or otherwise `blocked` dep are a *pending decision*, not a graph defect, and reporting them as a suspected cycle sends the operator hunting the wrong thing. Report those as `waiting behind a declared human gate: #N` (or the dep's blocker type) and reserve the cycle / unmet-external-dep diagnosis for rows whose deps are genuinely unreachable.

A `waiting` row is **not settled** — re-evaluated every resume (a dep may have landed) — but, unlike `blocked`, needs **no human reply** to promote; it auto-promotes when its deps are satisfied (`run-ledger.md`). The dep-gate is a pure eligibility filter, so re-runs never double-ship or double-post (the open-PR precheck still guards).

## Step 5 — Blocked-and-continue (don't stall the queue)

Autonomous is not reckless — but a blocker on one issue must not freeze the whole queue. **Per-issue blocker** (the type table in [blocker-protocol.md](blocker-protocol.md) is the single enumeration — read it there rather than working from a list here, so a type added later is picked up automatically): **do not stop.** Record a structured marker comment on the issue, set it `Blocked`, flip its ledger row, and **continue to the next item**. The human resolves it out-of-band; a later run resumes it idempotently. The marker format, blocker types, the scope-increase split rule, the anti-fear-descope guard, and the idempotent resume rule are in **[blocker-protocol.md](blocker-protocol.md)**.

**Stop the whole run only on a queue-wide failure:** `gh`/SSO/cloud auth expired mid-run, the concurrency lock is held by another session, a usage pause (Step 4), a **broken provenance stamp** on a `--from-rfc` table (Step 1 — a false verification claim is not something to drain past), or — in `--integration-branch` mode — a **base→integration sync conflict** (Step 4: a cross-team merge conflict is not the agent's to auto-resolve). These are not per-issue — pause-and-notify, do not burn the queue marking issues blocked. A `waiting` row is **not** a blocker and never triggers a stop (it is normal not-yet-ready state).

## Step 6 — Resume (`--resume`)

On a cron-fired resume after a usage pause: **first locate the ledger** — `--resume --session <id>` globs `.claude/triage/run-<label>-*<id>.md` for the *original* run's session id (a bare `--resume` globs `run-<label>*.md` and disambiguates by the `# resume-cmd` header; run-ledger.md "The ledger file"), **never** the resuming session's own `$CLAUDE_CODE_SESSION_ID`. Then **read its `# resume-cmd:` line and its `## operator-directives` / `## cross-slice re-scopes` / `## carry-forwards` sections** for the non-re-derivable narrative (these live in the ledger file, which outlives a compaction). Then rebuild slice state from the ledger + GitHub (`run-ledger.md` "reconstruct after compaction"), **then run Step 6.5 self-verification before trusting any row** — a ledger written before a crash can be stale; git + GitHub are the authority for merge state. Re-resolve the queue (Step 1, same label/scope), skip everything already shipped (open PR / `In Review`) or settled in the ledger, apply the [blocker-protocol.md](blocker-protocol.md) resume rule to any `Blocked` issue, and pick up any `In Progress` issue with a brief/worktree where it left off. **In `--integration-branch` mode**, also: sync base→integration first (Step 4), then **re-derive each `waiting` row's readiness from git reachability** (its deps' merge-commit SHAs) and promote any now-satisfied — a `waiting` row needs no human reply, unlike `blocked`. **In `--from-rfc` mode**, additionally **re-read the RFC Task Breakdown** and reconstruct the full slice set from it: un-created later-wave slices have neither an issue nor a ledger row, so the table — not the issue list — is the authority for what work remains; recompute readiness over the slice-ID DAG and create JIT issues for any slice now in the ready set. Re-arm the dead-man cron for the new window — carrying the same `--session <id>` from this ledger's `# resume-cmd:` header (the original run's id), never this resuming session's own `$CLAUDE_CODE_SESSION_ID`. When no open in-scope issue remains without a PR and without an unresolved blocker (and, in integration mode, no `waiting` row is still promotable — else it is a cycle, Step 4), **`CronDelete`** the dead-man cron and report.

## Step 6.5 — Self-verify the run state (unbiased agent)

The ledger is a cache; **git + GitHub are the authority.** Because a long unattended drain is compacted mid-run and a crash can leave a stale or wrong ledger, **validate the durable artefacts against ground truth with a *fresh, unbiased* subagent** — run this **on every resume / after any compaction, and once before opening the final integration→base-branch PR** (and optionally at the end-of-run report). It is the check that makes compaction survival trustworthy, not hopeful.

- **Spawn a fresh `general-purpose` subagent that has *not* seen the run's in-context history.** Give it only: the ledger path, the queue label/scope, the integration branch name, **and (in `--from-rfc` mode) the RFC path** — without the RFC the verifier cannot re-derive *un-created* slices (those with a `slice` ID but no issue/row yet) and would wrongly treat pending later-wave work as absent/drained. Instruct it to **re-derive the true state from git + the GitHub API *first*, without reading the ledger as truth**, then diff its independent finding against the ledger and return a **structured divergence report** (verdict-only; no raw dumps into the main context). It must check, per row:
  - `done` (flat) ⇒ the row's PR exists, is OPEN-or-MERGED to the base branch, and `Closes #<issue>` is wired; `done` (integration) ⇒ the recorded **merge-commit SHA is reachable from the integration branch** (`git merge-base --is-ancestor <SHA> origin/<integration>`), the slice PR is **Closed**, the issue is **Closed**, and the slice branch is gone.
  - `waiting on #M` ⇒ `#M` is genuinely **not** yet satisfied (its merge SHA is *not* reachable from integration / its issue still open); a `waiting` row whose deps ARE satisfied is a **missed promotion** — flag it.
  - `ready` / `in-progress` ⇒ no open PR already shipped it (else it is really `done`/`skipped`); the issue-keyed brief / panel dir / worktree are present-or-derivable.
  - **Orphans:** an integration merge-commit with no `done` ledger row (a slice merged but the row never flipped — a crash between push and ledger-write); a closed issue with no row.
  - **Excluded terminal slices (coverage gap) — *only* when operator-backed.** A slice missing from the shipped set at final completion — an `excluded` row, **or** (in `--from-rfc` mode) an RFC Task-Breakdown slice with **no** ledger row, especially a **testing or rollout** terminal (a `T*`/`R*`-class slice, an integration-suite or rollout-runbook row) — is a benign **coverage gap *only if backed by operator evidence*** (a `--exclude <slice>` flag or a durable issue/RFC marker, run-ledger.md "status"). With that backing, surface it as an explicit coverage-gap line (`coverage-gap: T1 (integration suite) excluded by operator — feature ships without it`) — a conscious operator decision, and the one Step-6.5 finding that is reported-but-not-corrected (nothing in the ledger to fix — the gap is real). **Without** operator backing it is **not** a gap but a real **divergence**: a missing/unledgered slice means the drain is incomplete (Step 4 — a queue with un-promoted table rows is *not* drained), so **fail completion**, never wave an un-shipped slice through as a self-granted "gap".
  - **Cross-slice re-scopes:** for every re-scope row (run-ledger.md "cross-slice re-scopes") whose `to` slice has **merged** — `pending` *or* `landed` (a stale ledger can mis-claim `landed`) — its `item` symbol must be in `to`'s first-parent merge diff (`git diff <to-merge-sha>^1 <to-merge-sha> | grep -Fq <item>`). Absent ⇒ a **dropped hand-off — fail the drain** (or downgrade a wrongly-`landed` row) and surface it; this gate runs before the final integration→base-branch PR, so a deferred scope cannot silently vanish. Judge "has `to` merged?" by `to`'s **reachable `merge` SHA**, not the `landed?` string: a row whose `to` has no reachable SHA is in-flight, **not** a failure (so a mid-drain resume never false-fails it) — except a row *claiming* `landed` with no reachable SHA, which is a contradicted-`landed` divergence (flag, do not diff a blank SHA). A `to = follow-up:#NNNN` row is exempt **only when bound to evidence** — `#NNNN` exists, is open, and is not a slice in this drain — else the in-diff check applies (run-ledger.md has the full gate).
- **Ground truth wins.** On divergence, **correct the ledger to match git+GitHub** (never the reverse), record what was corrected, and re-evaluate readiness from the corrected state. A `done`-claim that fails its reachability/closed check is **downgraded** (e.g. to `in-progress`) so the loop re-ships rather than advancing a wave on a phantom merge.
- **Surface, don't silently fix the world.** The agent corrects the *ledger* (local cache); it does **not** merge, close, or push to reconcile GitHub — a real divergence (e.g. a `done` row whose merge vanished) is reported to the operator. Self-verification fixes our *model* of reality, it does not mutate reality.

The schema of the divergence report and the exact reachability commands are in [run-ledger.md](run-ledger.md) "self-verification".

## Step 6.6 — Whole-integration adversarial review (`--integration-branch` mode, before the final PR)

Step 6.5 re-derives **merge state** (is every slice reachable, closed, its handoffs landed) — it does **not** review the **assembled feature**. Per-slice panels review each slice's *own diff*; by construction they cannot see a defect that **emerges only from the slices composed together**. So before opening the integration→base-branch PR, fan the full review-panel over the **entire** integration diff **once** — this is additive to the per-slice panels, not a re-run of them.

- **Run `/review:review-panel` `pre-pr` over the whole integration diff**, from the integration worktree (Step 1): `MB=$(git -C "$INT" merge-base "origin/$BASE" HEAD); git -C "$INT" diff "$MB"`. Its Step 2 routes the fitting lens set over the aggregate — this is the **complete** routed set a normal pre-pr panel would apply to this file-set (correctness, security, architecture, tenant scoping, the judgment lens, the skeptic pass, whatever the routing selects), **not** a composition-only subset. **Do not shrink it to the cross-slice framing below** — a correctness / security / tenant defect can live in the composed code without being a "seam" per se, so the full routing must run over the aggregate. **Also run its Step 2.6 cross-model lenses** (the counterpart and OCR engines, as the `/review:review-panel` skill specifies) as separate background calls over the same diff. Token isolation is the same as the per-slice panel: lens subagents write to disk and return counts; the main loop reads only the consolidated Critical/Important.
- **Additionally frame the pass at what per-slice review is blind to** — this is **extra emphasis layered on the full routed set above, not a narrower lens selection**; do **not** re-litigate clean per-slice detail, but do prioritize:
  1. **Cross-slice seams** — a defect from *composing* two independently-reasonable slices: a write cadence one slice changed that another slice's cost now multiplies (an order-total recount once per run becoming once per page), an inconsistent choice across siblings (an order-export script reading every tenant's rows while its mutating sibling uses the enforced tenant scope), a race spanning two scripts.
  2. **Each slice's deliverable-completeness vs its Task-Breakdown row** — per-slice review checks what a slice *changed*, never what it was *supposed* to change. Re-read each slice's Task-Breakdown deliverable and confirm it actually shipped (a slice mandated to fix a stale doc line that edited the file but left the line).
  3. **A doc that states a not-yet-true end state as current fact** (an orders doc describing the shape after a cleanup that has not shipped) and **an alert that misses a failure mode** its sibling alert catches.
- **Fix Critical/Important in the integration worktree main loop, then re-run the merge gate** on the new tip (Done's re-entrant gate). Only then open the PR.

This is not optional rigor: defects that exist only in the composition — a cross-slice per-page query regression, a scope inconsistency on a destructive path, a slice that under-delivered its own deliverable, a cleanup race spanning two slices — are structurally invisible to the per-slice panels and to Step 6.5. This pass is the only place they surface.

## Course-correction (mid-run, operator-directed)

An author may redirect an **in-flight** drain — and it must be handled gracefully, not ignored or applied half-way. The instruction can be about anything: a **task** (skip #X, also do #Y, redo #X with a corrected brief, re-prioritise), a **dependency** (#C no longer depends on #A; #C now depends on #D), **scope** (the brief is wrong — re-ground), a **branch/PR** (a slice went to the wrong branch; retarget a PR base; rename the integration branch), or **stop** (abort the run). Three rules make it safe:

1. **Record the directive durably the instant it arrives** — append it to the ledger `## operator-directives` table as `pending` **before acting** ([run-ledger.md](run-ledger.md) "course-correction"), so a compaction mid-fix cannot lose it; it is replayed on resume like any durable state.
2. **Apply at the next *clean checkpoint*, never mid-fix.** A fix in flight either finishes or is explicitly abandoned (worktree discarded) first — never leave a half-applied edit. Then flip the directive `pending → applied`. Acknowledge to the operator what will change and when it takes effect (this checkpoint vs the next).
3. **Re-derive, then re-verify.** Any task/dep/scope/skip/add change **re-runs readiness** (a dropped dep can promote a `waiting` row; an added task inserts a row the `--strategy` then orders; a re-ground rewrites the brief) **and re-runs Step 6.5 self-verification** so the ledger still matches ground truth afterward.

**Per scenario:** *skip/drop* — remove from the ready/waiting set, leave the issue open, note it; *add* — inject a row, parse its `Depends-on`, slot it by readiness+strategy; *re-prioritise* — reorder the ready set only (waiting stays gated); *change a dep* — rewrite the row's `Depends-on`, re-derive readiness (may promote or re-park dependents); *re-ground/scope* — discard the stale brief, re-ground (route by Implementing skill, Step 2), rebuild; *retarget/rename branch* — `gh pr edit --base` / update the ledger header.

**Irreversibility guard (the load-bearing one):** a directive touching an **already-merged-to-integration** slice (drop it, move its branch) **cannot be silently un-done** — ship-queue does **not** autonomously rewrite integration history. Surface it: the slice's commits are in integration; backing it out is an **explicit operator-confirmed** revert (a `git revert <merge-sha>` or a revert slice), not an auto-rewrite — and that confirmation is **recorded as its own ledger directive row** (`revert #X — confirmed-by <human> at <ISO>`) so it is durable and auditable, never a self-grant. Same posture as self-verification — we change our *model* (the ledger) freely; we change *merged reality* only with a human go-ahead. An **abort** stops at the next clean checkpoint, leaves shipped slices on integration, opens (or leaves open) the integration→base-branch PR for the human, and reports — it does not unwind merged work.

## Done

Report from the ledger, per issue: PR URL, merge gate verdict, review-panel + Codex-sweep outcome; any **blocked** items with the marker reason (these stay open for the human, the run did not stall on them); any skipped/escalated items; any usage pauses (with resume time). **Render each row's bare `PR#` as a clickable `https://github.com/<owner/repo>/pull/<PR#>`** — the number is the durable ledger key, so the URL is derived at report time; **no URL column is stored** (a second copy of the same fact would drift). The queue is drained when no open in-scope `<queue-label>` issue remains without a PR and without an unresolved blocker marker.

**In `--integration-branch` mode**, before reporting: run Step 6.5 self-verification and the **Step 6.6 whole-integration adversarial review** (fix its Critical/Important on the integration branch first), then **open (never merge) the single integration→base-branch PR** from the **integration worktree** (Step 1) — `gh pr create --base "$BASE" --head <integration>` with a body summarising every slice merged onto it.

**Announce that final PR with `/ship:pr`'s exact one-line format — never a free-drafted chat post.** Because this step opens the PR with `gh pr create` directly (the inline write-path), it bypasses `/ship:pr` and so must **replicate `/ship:pr`'s announce step**: a **single line** in `/ship:pr`'s format to the `announce_channel` setting's channel (blank skips it), matching every other announce in the channel. Operator-facing notes (e.g. "needs the merge gate trigger before merge", "deploy backend-first") belong in the **PR body**, **not** the channel announce — a multi-paragraph post is the wrong shape and forces a hand-edit. The per-slice PRs stay announce-suppressed by design (internal, closed-not-merged); this announce is the integration→base-branch PR only.

**When the drain owns a whole RFC** (`--from-rfc`, or an `--integration-branch` drain of an RFC's breakdown), two RFC-tail steps ride this finish (both defined in `task-breakdown`'s contract — this is just where the drain executes them): (a) the **harness-education terminal slice** — shipped as the last slice before this PR — re-grounds against the drain's accumulated per-slice panel findings on disk, so any defect *class* the panels flagged more than once across slices graduates to a rule/lint in that slice (the contract's promotion trigger), not a prose note; and (b) flip the RFC's `Status:` front-matter to `Implemented` **as part of this PR's diff** — commit it on the integration branch before opening the PR so it lands atomically when the human merges, never a separate edit and never before the drain completes. The slice issues were already **explicitly closed at merge time** (Step 3.6), so the source of truth for closure is that step; a `Closes #<each-slice-issue>` line in this PR body is harmless belt-and-suspenders (a no-op on already-closed issues), not the closing mechanism — do not rely on it, and if a slice issue is unexpectedly still open at this point, treat it as a self-verification divergence (Step 6.5), not something the final PR will silently fix. **Gate the final aggregate diff like any other PR:** run the merge gate on this integration→base-branch PR **as a zero-token background Bash** (same as Step 6 — not an LLM subagent) — its cross-slice + base-sync combination is a real diff the per-slice runs never saw — and **report its verdict**; do **not** call the drain complete on an ungated final PR.

**The final PR is a re-entrant gate, not a one-shot — marking it ready is not terminal.** Any commit that lands on the integration branch *after* the ready-flip — a post-ready Codex-fix round, a late base→integration sync, a review fix — **leaves the merge gate result behind the integration tip and re-runs this step on it**: refresh the PR body to the new diff and re-run the merge gate on the new HEAD (the prior green was on the old tip), and re-run Step 6.5 self-verification if slices merged after the flip. The drain is **not** complete while the final PR's merge gate result sits behind the integration tip — a "READY for human" that a later fix round silently staled is the endgame failure this prevents. If your merge gate needs a manual trigger on a base-branch PR (a label named in `merge_gate`), applying it together with merge is the **human's** step. The agent does not run `gh pr merge`, so this base-branch gate is **human by construction** — the human reviews, triggers the gate if needed, and merges. The end report then adds: the integration branch state (N ahead of the base branch, last synced), the opened integration→base-branch PR URL **+ its merge gate verdict + any gate trigger the human still owes before merge**, any rows still `waiting` (with the merges that would release each) or a reported cycle, any **coverage gaps from operator-excluded terminal slices** (Step 6.5 — e.g. an excluded integration-suite or rollout-runbook slice), and any base→integration sync conflict that paused the run. The drain is complete when every promotable slice is merged onto integration and that one PR is open for human review — **not** when it merges (that is the human's call).
